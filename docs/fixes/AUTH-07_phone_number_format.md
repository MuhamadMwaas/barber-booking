## 1. الحل المقترح في التقرير كان سيُعطِّل كل مستخدم قائم

اقترح التقرير:

```php
'regex:/^\+[1-9]\d{7,14}$/',   // E.164
```

التعبير **صحيح كتعريف لـ E.164**، لكنه **مُطبَّق على الشيء الخطأ**: على النصّ الخام كما كتبه
المستخدم.

قِسْتُ ذلك على قاعدة البيانات الفعلية:

```
total: 25
strict E.164: 0
NOT E.164: 25

  +971-50-101-0101
  +971-50-111-1111
  +971-50-123-4567
  ...
```

**صفر من 25.** والسبب ليس إهمالاً — بل قرار معماري موثَّق في [`config/sms.php`](../../config/sms.php):

> «أرقام الهاتف في قاعدة البيانات هذه مخزَّنة للبشر لا للبوّابات — مثلاً `+971-50-101-0101`.
> البوّابات تريد أرقام E.164 مجرّدة، لذا يُطبَّع كل رقم قبل إرساله.»

فالتطبيع يحدث **عند حافّة بوّابة الرسائل**، والتخزين يبقى بصيغة بشرية.

**الأثر لو طُبِّق التعبير حرفياً:** كل عميل يفتح شاشة «تعديل الملف الشخصي» ويضغط «حفظ» يرسل
رقمه الحالي دون تغيير ضمن الحمولة — فيتلقّى **422**. لا يستطيع تعديل مدينته ولا اسمه. إصلاحٌ
أمني يُعطِّل كل مستخدم قائم ليس إصلاحاً.

## 2. ما فُعِل بدلاً منه: طبِّع أولاً ثم تحقّق

[`app/Rules/PhoneNumber.php`](../../app/Rules/PhoneNumber.php):

```php
public static function isValid(?string $phone): bool
{
    return preg_match('/^\+[1-9]\d{7,14}$/', self::normalize($phone)) === 1;
}
```

نفس تعريف E.164 من التقرير — لكن **الموضوع** صار الرقم بعد التطبيع لا النصّ الخام.
**علامات الترقيم التي يضيفها إنسان ليست خاصيّة أمنية؛ الأرقام تحتها هي الخاصيّة.**

### لماذا `PhoneNumberNormalizer` تحديداً لا تطبيعاً جديداً

إعادة استخدام [`Services\Sms\PhoneNumberNormalizer`](../../app/Services/Sms/PhoneNumberNormalizer.php)
هي **جوهر الحل لا اختصارٌ فيه**: تعني أن كل رقم يجتاز التحقق هو — بحكم البناء — رقمٌ تستطيع
بوّابة الرسائل أن تُوصِّل إليه رمز OTP فعلاً. مُدقِّقٌ يقبل أرقاماً ترفضها البوّابة لاحقاً لا
يمنع شيئاً، بل ينقل الفشل إلى حيث لا يراه أحد.

> `ThrottleKey` تُجري تطبيعها الخاص عمداً — مفتاح الحدّ يجب أن يُشتقّ من مُدخَل مشوَّه أيضاً،
> وهذا بالضبط وقت الحاجة إليه. لا تناقض بين الاثنين.

### السلوك المقيس

| المُدخَل | التطبيع | النتيجة |
|---|---|---|
| `+971-50-101-0101` | `+971501010101` | ✅ (الصيغة الموجودة في قاعدة البيانات) |
| `+971501010101` | `+971501010101` | ✅ |
| `00971501010101` | `+971501010101` | ✅ (بادئة النفاذ الدولي) |
| `971501010101` | `+971501010101` | ✅ |
| `+49 (0) 30 1234567` | `+490301234567` | ✅ |
| `0501010101` | `0501010101` | ❌ صيغة محلية بلا `SMS_DEFAULT_COUNTRY_CODE` — **لا سبيل لمعرفة الدولة** |
| `+0123456789` | `+0123456789` | ❌ رمز دولة يبدأ بصفر |
| `+12345` | `+12345` | ❌ أقصر من E.164 |

## 3. مسار كتابة واحد لا يكفي — نفس درس AUTH-06

التقرير أشار إلى `ProfileController` وحده. لكن `users.phone` يُكتَب من **ثلاثة** مواضع:

| الملف | ما كان عليه |
|---|---|
| `ProfileController::update()` | `'sometimes','string','max:20'` — بلا صيغة |
| `PhoneVerificationController::sendOtp()` | `'sometimes','string','max:20'` — بلا صيغة، **ويكتب الرقم مباشرةً عبر `forceFill()`** |
| `RegisterRequest` | `'string','max:255'` — **بلا أي تحقق إطلاقاً**، وهنا يدخل الرقم أول مرة |

القاعدة الآن على الثلاثة. `RegisterRequest` هو الأهم فعلياً: الرقم الداخل عند التسجيل هو الرقم
الذي تُرسَل إليه كل رموز OTP لاحقاً.

## 4. ما لم يُصلَح هنا — وهو الأعمق (يستحق بنداً مستقلاً)

**`users.phone` لا يزال بلا صيغة معياريّة في التخزين.** والنتيجة:

```
+971501010101      ← حساب أ
+971-50-101-0101   ← حساب ب
```

**نفس الرقم الحقيقي، صفّان مختلفان.** و`Rule::unique('users','phone')` تقارن نصّاً خاماً، فلا
تمنع ذلك. وبما أن الهاتف **هويّةُ دخول** (`AuthController:69`) و**هدفُ OTP**
(`OtpController:41,86,136`)، فهذا **تجاوزٌ لقيد التفرّد**: يستطيع مهاجم فتح حساب ثانٍ على رقم
شخص آخر بكتابته بصيغة أخرى.

**لماذا لم يُصلَح ضمن AUTH-07:** الإصلاح الصحيح هو تخزين الصيغة المعياريّة — وهذا يستلزم
تطبيع **كل مواضع البحث** أيضاً (`where('phone', $input)` في تسجيل الدخول والـ OTP)، وميجريشن
يُعيّر الصفوف القائمة مع كشف التصادمات قبل الكتابة. تخزينٌ مُطبَّع بلا بحثٍ مُطبَّع = **كسر
تسجيل الدخول** لكل من غيّر رقمه.

الأداة جاهزة (`PhoneNumber::normalize()`)، والاختبار
`test_equivalent_spellings_share_one_canonical_form` يثبّت سلوكها استعداداً لذلك.

## 6. الاختبارات

17 اختباراً، والأهم فيها ليس اختبارات الرفض بل هذا:

```
✓ a real international number is accepted
    with data set "human separators (the form already in the database)"
```

**هذا الاختبار هو الحارس ضد الحل المقترح في التقرير.** أي محاولة مستقبلية لاستبدال القاعدة
بتعبير نمطي على النصّ الخام ستُسقطه فوراً.

ويؤكّد كل اختبار رفض أن الرقم المخزَّن لم يتغيّر — أي أن الرفض حدث قبل أي كتابة، ويتحقق
`test_a_rejected_phone_rolls_back_the_whole_profile_update` من أن الحقول المرافقة لم تُكتب
جزئياً.
