## 1. تصحيحان على نصّ التقرير الأصلي

قبل أي شيء: **المشكلة الثالثة في التقرير غير صحيحة.**

### التصحيح الأول — «تغيير كلمة المرور لا يُبطل الجلسات» ❌ خطأ

اقتبس التقرير هذا الكود من `ProfileController`:

```php
$user->password = bcrypt($request->password ?? "");
$user->save();
// لا $user->tokens()->delete();  ولا إبطال لتوكنات التحديث
```

الكود الفعلي في الملف كان — **قبل أي تعديل منّي**:

```php
$user->password = bcrypt($request->password??"");
$user->save();
$user->tokens()->delete();                              // ← موجود
$user->refreshTokens()->update(['revoked' => true]);    // ← موجود
```

السطران كانا موجودين. الاقتباس في التقرير قديم أو مُختلق، والوصف «يبقى توكن وصوله وتوكن تحديثه صالحين» **لم يكن صحيحاً**.

وينطبق الشيء نفسه على `PasswordResetService::resetPassword()` و`AuthController::logout()` — كلاهما كان يُبطل النوعين بالفعل.

**ما فعلته هنا بدل ذلك:** أبقيت السلوك، وأضفت له **سبب الإبطال** (`revoked_reason`)، لأن كشف إعادة الاستخدام لا يعمل بدونه — الفقرة 4 تشرح لماذا.

كما أنني **لم آخذ** باقتراح التقرير باستثناء الجلسة الحالية:

```php
$user->tokens()->where('id', '!=', $currentTokenId)->delete();   // ← لم أطبّقه
```

السبب: من يُغيّر كلمة المرور بعد اشتباه باختراق لا يعرف أيّ الجلستين جلسته. استثناء «الحالية» يعني الوثوق بأن مَن أرسل الطلب هو صاحب الحساب — وهو بالضبط الافتراض الذي جاء تغيير كلمة المرور ليُلغيه. إنهاء **كل** الجلسات وإعادة تسجيل الدخول مرّة واحدة ثمن زهيد مقابل يقين كامل.

### التصحيح الثاني — الحل المقترح في التقرير فيه ثغرتان

الكود المقترح في التقرير **لا يصلح للتطبيق كما هو**:

| المشكلة | الأثر |
|---|---|
| `$token->update(['revoked' => true])` — قراءة ثم كتابة بلا شرط | طلبان متزامنان يحملان نفس التوكن **يُدوّران كلاهما**، فينتهي الحساب بعائلتَي توكن حيّتين — وهي بالضبط الحالة التي جاء التدوير ليمنعها |
| أي توكن مُبطَل يُشعل الإنذار | **كل تسجيل خروج** يتبعه إعادة محاولة من عميل قديم يُقرأ كسرقة، فتُدمَّر جلسات المستخدم بلا سبب |

الفقرتان 3 و4 تشرحان كيف عالجتُ الاثنتين.

## 3. الإصلاح الأول — التدوير

### المبدأ

توكن التحديث صار **صالحاً لاستعمال واحد**. كل نداء لـ `/api/auth/refresh` يقتل التوكن الذي وصل به ويُعيد واحداً جديداً.

هذه الخاصية الواحدة هي كل شيء: **متى صار التوكن يُنفَق مرّة واحدة، صار ظهوره مرّة ثانية دليلاً قاطعاً على وجود نسخة منه.** لا يوجد تفسير آخر. من هنا يولد كشف إعادة الاستخدام في الفقرة 4 — التدوير ليس حماية بذاته بقدر ما هو **ما يجعل السرقة قابلة للرؤية**.

### الكتابة الشرطية — لماذا لا `$token->update()`

```php
// app/Services/AuthTokenService.php
$claimed = RefreshToken::query()
    ->whereKey($token->getKey())
    ->where('revoked', false)        // ← الشرط هو كل الحكاية
    ->update([
        'revoked'        => true,
        'revoked_at'     => now(),
        'revoked_reason' => RefreshToken::REASON_ROTATED,
        'last_used_at'   => now(),
    ]);

if ($claimed !== 1) {
    return null;   // خسر السباق — طلب آخر أنفق هذا التوكن
}
```

`UPDATE ... WHERE revoked = false` عملية **ذرّية في قاعدة البيانات**. لو وصل طلبان في اللحظة نفسها بالتوكن نفسه — نقرة مزدوجة من عميل شرعي، أو اللص يسابق صاحب الحساب — فواحد فقط يمكن أن يرى صفّاً واحداً متأثراً. الآخر يرى صفراً، فيُخبَر أنه خسر ويُردّ بـ 401.

هذا هو الفرق الجوهري عن اقتراح التقرير: `$token->update(['revoked' => true])` يقرأ في PHP ثم يكتب، فلا يستطيع أن يمنع الطلب الثاني من الكتابة أيضاً. مع الكتابة الشرطية، **عملية تحديث واحدة تنجح لكل توكن، مهما بلغ التوازي**.

### التسلسل

بعد نجاح المطالبة، يُربَط التوكن المُنفَق بخَلَفه:

```php
RefreshToken::query()->whereKey($token->getKey())
    ->update(['replaced_by_id' => $new['id']]);
```

فتصير عائلة التوكنات قابلة للتتبّع من أوّلها إلى آخرها بعد أي حادث.

## 4. الإصلاح الثاني — كشف إعادة الاستخدام

### السؤال الذي يجب أن يُجاب

عند وصول توكن تحديث مرفوض، هناك **ثلاث حالات مختلفة تماماً** تختبئ خلف نفس الـ 401:

| الحالة | ماذا تعني | الرد الصحيح |
|---|---|---|
| 1. لم نُصدره قط، أو انتهت صلاحيته | ضجيج | 401 وانتهى |
| 2. أُبطل عمداً (خروج / تغيير كلمة مرور / إعادة تعيين) | عميل قديم لم ينتبه | 401 وانتهى |
| 3. **أُنفق في تدوير ناجح ثم عاد** | نسخة ثانية منه موجودة → **تسريب** | **إبادة كل جلسات الحساب** |

الحالة 3 هي الإنذار. ومنطقها حاسم: صاحب الحساب الشرعي **لا يستطيع** إنتاج توكن مُنفَق، لأننا سلّمناه بديله. فمن يقدّمه الآن يحمل نسخة لم تأتِ منّا.

والرد ليس رفض هذا الطلب وحده. الخادم **لا يعرف** أيّ الطرفين اللص وأيّهما الضحية — كلاهما يحمل توكناً صالح الشكل. فالجواب الوحيد الآمن هو إسقاط الطرفين معاً وإجبارهما على إعادة المصادقة. الضحية يعيد تسجيل الدخول؛ اللص لا يستطيع.

### لماذا `revoked_reason` شرط لا زينة

بدون هذا العمود **تنهار الحالتان 2 و3 في واحدة**، لأن العمود `revoked` وحده لا يفرّق بين توكن مات لأنه أُنفق وتوكن مات لأن المستخدم سجّل خروجاً.

النتيجة العملية لاقتراح التقرير (الذي يُشعل الإنذار على أي توكن مُبطَل): **كل تسجيل خروج عادي** يتبعه عميل يعيد المحاولة بالتوكن القديم — وهذا يحدث باستمرار — يُقرأ كسرقة، فيُدمّر جلسات المستخدم على كل أجهزته. نظام إنذار يرنّ على الأبرياء يُطفَأ خلال أسبوع.

مع العمود، الشرط دقيق:

```php
if ($record->revoked_reason !== RefreshToken::REASON_ROTATED) {
    return $rejected;   // إبطال متعمّد، لا سرقة
}
```

**فقط `rotated` دليل.** كل الأسباب الأخرى عميل قديم.

### نافذة السماح — الحالة البريئة الوحيدة

يبقى سيناريو واحد يُنتج توكناً مُنفَقاً عائداً بلا أي سرقة: العميل أرسل التحديث، ودوّرنا وردّينا، **وضاع الردّ في الطريق** — انقطاع، أو تطبيق ذهب للخلفية، أو تنقّل بين أبراج شبكة. العميل لم يرَ توكنه الجديد قط، فيعيد المحاولة بالقديم بحسن نيّة تامّة.

```php
$graceSeconds = (int) config('auth_tokens.reuse_grace_seconds', 60);

if ($record->revoked_at && $record->revoked_at->gt(now()->subSeconds($graceSeconds))) {
    return $rejected;   // 401 صامت — لا إنذار، ولا مساس بالأجهزة الأخرى
}
```

داخل 60 ثانية: 401 عادي، والعميل يعيد المصادقة، **ولا يُمسّ أي جهاز آخر**. خارجها: المهاجم كان لديه وقت كافٍ ليتصرّف، فيرنّ الإنذار.

هذه النافذة هي المفاضلة الوحيدة في الإصلاح كلّه: كلما اتّسعت، طالت المدّة التي يستطيع فيها توكن مسروق فعلاً أن يُعاد بلا كشف. لذلك هي 60 ثانية، لا أكثر.

### السجلّ

عند الإنذار يُكتب في `laravel.log` كل ما يلزم للتحقيق:

```php
Log::warning('Refresh token reuse detected: revoking all sessions for the account', [
    'user_id'            => $record->user_id,
    'refresh_token_id'   => $record->id,
    'rotated_at'         => $record->revoked_at?->toDateTimeString(),
    'issued_to_device'   => $record->device,       // من صدر له أصلاً
    'issued_to_ip'       => $record->ip,
    'replayed_from_ip'   => request()->ip(),       // من أعاده الآن
    'replayed_by_device' => request()->header('User-Agent'),
]);
```

المقارنة بين `issued_to_ip` و`replayed_from_ip` تُظهر عادةً الفرق بين الضحية واللص مباشرة.

## 5. الإصلاح الثالث — إخراج `APP_KEY` من التجزئة

### قبل

```php
$hashed = hash('sha256', $plain . config('app.key'));
```

### بعد

```php
public function hash(string $plain): string
{
    return hash('sha256', $plain);
}
```

التقرير محقّ تماماً: التوكن أصلاً **64 حرفاً من مولّد عشوائي مُؤمَّن**، فلا يوجد قاموس تُحمى منه التجزئة، وخلط سرّ فيها لا يضيف قوّة. لكنه يضيف عطباً: تدوير `APP_KEY` إجراء قياسي بعد أي اشتباه بتسريب المفتاح — ومع المفتاح داخل التجزئة، ذلك التدوير **يُبطل صامتاً كل توكنات التحديث في قاعدة البيانات ويُخرج كل زبون بلا تفسير**. لا يصحّ أن يُوزَن إجراء أمني مقابل تسجيل خروج جماعي قبل استعماله.

### الهجرة بلا تسجيل خروج جماعي

تغيير طريقة التجزئة يُخرج — عادةً — كل من يحمل توكناً قديماً. تجنّبتُ ذلك بقبول التجزئتين عند البحث:

```php
private function candidateHashes(string $plain): array
{
    return [
        $this->hash($plain),                        // الجديدة
        hash('sha256', $plain . config('app.key')), // القديمة — ما قبل AUTH-04
    ];
}
```

والتدوير **يُصفّي الدَّين وحده**: أول تحديث يُعيد إصدار التوكن بالصيغة الجديدة، فتنزح الصيغة القديمة من الجدول تلقائياً كلما عاد العملاء، وتختفي نهائياً بانتهاء صلاحية آخر توكن قديم (30 يوماً كحدّ أقصى). لا حاجة لأي تدخّل.

> اختبار `test_rotating_a_token_does_not_depend_on_the_app_key_staying_put` يُبدّل `APP_KEY` فعلياً أثناء التنفيذ ويتحقّق أن التحديث ما زال يعمل.

## 6. عطب كامن اضطررت لإصلاحه أولاً — `expires_at` يُعيد كتابة نفسه

هذا **لم يكن في التقرير**، ووجدته أثناء العمل. ولولا إصلاحه لما صحّ التدوير.

الجدول الأصلي كتب:

```php
$table->timestamp('expires_at');
```

و`expires_at` هو **أول عمود `TIMESTAMP NOT NULL`** في `refresh_tokens`. مع `explicit_defaults_for_timestamp = OFF` (الافتراضي على هذا الخادم) تُلصق MySQL به تلقائياً `DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP`. الفحص على المخطّط الحيّ قبل الإصلاح:

```sql
`expires_at` timestamp NOT NULL
    DEFAULT current_timestamp() ON UPDATE current_timestamp()
```

**نفس العطب المُصلَح على `otps.expires_at` سابقاً** — وهو أحد الأعمدة الأربعة التي كانت مُبلَّغة ككامنة.

### لماذا كان كامناً ولماذا لم يعد

حتى الآن، كل `UPDATE` يجريه الكود على توكن تحديث كان **يُبطله في الوقت نفسه**، فتشويه تاريخ الانتهاء لا يغيّر شيئاً: الصفّ ميت أصلاً.

التدوير ينهي ذلك. التدوير يكتب في صفّ التوكن ثم **يظلّ يقرأ عمره** — `revoked_at` و`expires_at` كلاهما يُستَشار بعد الكتابة. عمود يتحرّك من تحت القراءة لا يمكن الوثوق به.

### الإصلاح

```php
DB::statement(
    'ALTER TABLE `refresh_tokens` MODIFY `expires_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP'
);
```

`DEFAULT` صريح هو ما **يُلغي** الزوج التلقائي. القيمة الافتراضية نفسها لا يُعتمد عليها أبداً — `AuthTokenService` يُمرّر `expires_at` دائماً — وجودها فقط ليمنع `ON UPDATE` من العودة.

> `$table->timestamp('expires_at')->change()` **لا يصلح** هنا: يُصدر `TIMESTAMP NOT NULL` مجرّداً فيُعيد إشعال القاعدة نفسها. لذلك SQL خام.

### المخطّط بعد الميجريشن (تحقّق فعلي)

```sql
`expires_at`     timestamp NOT NULL DEFAULT current_timestamp(),   -- ON UPDATE اختفى ✅
`revoked`        tinyint(1) NOT NULL DEFAULT 0,
`revoked_at`     timestamp NULL DEFAULT NULL,
`revoked_reason` varchar(32) DEFAULT NULL,
`last_used_at`   timestamp NULL DEFAULT NULL,
`replaced_by_id` bigint(20) unsigned DEFAULT NULL,
KEY `refresh_tokens_user_id_revoked_index` (`user_id`,`revoked`)
```

الأعمدة الجديدة كلها `nullable`، وهي **معفاة** من قاعدة MySQL أعلاه (تُصاغ `NULL DEFAULT NULL` بلا أي إضافة تلقائية).

### الصفوف القديمة

```php
DB::table('refresh_tokens')
    ->where('revoked', true)->whereNull('revoked_reason')
    ->update([
        'revoked_reason' => 'legacy',
        'revoked_at'     => DB::raw('COALESCE(`updated_at`, `created_at`)'),
    ]);
```

تُملأ كإبطال متعمّد، **لا كتدوير أبداً**: التدوير لم يكن موجوداً حين أُبطلت، فلا يمكن أن تكون دليل تسريب، ولا يجوز أن تُشعل الإنذار بأثر رجعي.

## 9. ⚠️ عقد العميل — الجزء الوحيد الذي يحتاج انتباهك

استجابة `POST /api/auth/refresh` **تحمل الآن حقلين جديدين**:

```jsonc
{
  "access_token": "...",
  "access_expires_at": "2026-08-29 20:15:00",
  "refresh_token": "...",              // ← جديد — يجب حفظه
  "refresh_expires_at": "2026-09-28 20:00:00",   // ← جديد
  "requires_otp_verification": false
}
```

**على تطبيق الموبايل أن يحفظ `refresh_token` العائد ويستعمله في المرّة القادمة.** التوكن الذي أرسله للتوّ صار ميتاً.

### ماذا يحدث لبناء قديم لا يحفظه؟

1. يُحدّث بتوكنه الأصلي → ينجح، ويتجاهل الجديد.
2. بعد 15 دقيقة يُحدّث **بالتوكن الأصلي نفسه** — وهو الآن مُنفَق، وخارج نافذة الستين ثانية.
3. **يُقرأ كتسريب** → تُبطل كل جلسات ذلك المستخدم → خروج كامل من كل الأجهزة.

هذا ليس عطباً، بل السلوك المقصود بالضبط — لكنه سيصيب المستخدمين الحقيقيين إن نُشر الخادم قبل التطبيق.

### مفتاح الأمان أثناء الانتقال

```env
AUTH_ROTATE_REFRESH_TOKENS=false
```

يُعيد السلوك القديم تماماً (استجابة بلا `refresh_token`، والتوكن يبقى حيّاً بعد استعماله). كل ما عداه من الإصلاح — إخراج `APP_KEY`، إصلاح `ON UPDATE`، أسباب الإبطال — يظلّ فعّالاً.

**الترتيب الموصى به:**

1. انشر الخادم بـ `AUTH_ROTATE_REFRESH_TOKENS=false`.
2. أطلق بناء التطبيق الذي يحفظ التوكن الجديد.
3. انتظر حتى يُحدِّث معظم المستخدمين.
4. اقلب المفتاح إلى `true` (وهي القيمة الافتراضية، فيكفي حذف السطر).

إن كان التطبيق ما زال قيد التطوير ولا توجد بناءات في الميدان، اتركه على `true` من الآن.

## 10. الضبط من `.env`

كل القيم لها افتراضيات معقولة، ولا يلزم أي متغيّر جديد للعمل.

| المتغيّر | الافتراضي | ما يفعله |
|---|---|---|
| `AUTH_ACCESS_TTL_MINUTES` | `15` | عمر توكن الوصول |
| `AUTH_REFRESH_TTL_DAYS` | `30` | عمر **العائلة** لا التوكن الواحد (كل توكن يموت عند أوّل استعمال) |
| `AUTH_ROTATE_REFRESH_TOKENS` | `true` | مفتاح التدوير — انظر الفقرة 9 |
| `AUTH_REFRESH_REUSE_GRACE_SECONDS` | `60` | نافذة السماح — كلما اتّسعت طال بقاء توكن مسروق بلا كشف |

## 12. ثغرة مجاورة وجدتها ولم أُصلحها

**`refresh` لا يفحص `is_active`.**

`login` يردّ 403 `account_disabled` على حساب مُعطَّل ([`AuthController::login`](../../app/Http/Controllers/Api/AuthController.php)) — لكن `refresh` **لا يفحص هذا الحقل إطلاقاً**. النتيجة: حساب عُطّل من لوحة الإدارة يستطيع صاحبه الاستمرار في تجديد توكنات الوصول حتى انتهاء عائلة التحديث — **حتى 30 يوماً بعد التعطيل**.

هي من عائلة AUTH-04 نفسها (إبطال الجلسات)، لكنها **خارج نطاق ما طلبتَه**، وإضافتها تغيّر سلوكاً قد تعتمد عليه أجزاء أخرى. الإصلاح سطران داخل `refresh()` بعد جلب المستخدم:

```php
if (! $user->is_active) {
    return response()->json(['message' => __('auth.account_disabled')], 403);
}
```

الأصحّ منه: إبطال جلسات المستخدم لحظة تعطيله من لوحة الإدارة، لا انتظار محاولة التحديث التالية. قل لي إن أردتها.
