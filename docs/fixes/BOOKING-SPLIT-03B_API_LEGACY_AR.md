## السؤال 1 — عقد API: ماذا نرجع من `POST /api/bookings`؟

**نص السؤال حرفيًا:**
> الحجز قد ينتج الآن أكثر من موعد. ماذا نرجع للاستجابة؟ `POST /api/bookings`

**لماذا يُسأل؟**
اليوم `BookingController::store()` في `app/Http/Controllers/Api/BookingController.php:32-57` يرجع `201 + AppointmentResource` مفرد (صف واحد). بعد الحل 3 قد يُنتج الطلب الواحد صفين (أب 09:40–10:00 + ابن 15:10–15:45). العقد الجديد يجب أن يبقي التطبيق الحالي يعمل دون تحديث إجباري، ويعطي التطبيق الجديد ما يكفي لعرض الكتلتين وربطهما.

### الخيار 1 — متوافق خلفيًا + حقول جديدة (Recommended)

**النص حرفيًا:**
> يبقى الموعد الأب (نفس الشكل الحالي، والتطبيق القديم يبقى يعمل) تُضاف حقول للأبناء (`linked_appointments`, `parent_appointment_id`, `group_root_id`, `is_child_booking`, `group_total_amount`) إلى `AppointmentResource`. القوائم تعرض كل كتلة كقطاعات منفصلة تلقائيًا.

**الشرح المفصل:**
يبقى شكل الـ `data` كما هو اليوم (كائن واحد = الأب بنفس الحقول: `id/number/start_time/end_time/services_details/...`) فلا ينكسر أي parse لدى النسخ القديمة. تُضاف حقول اختيارية جديدة يجهلها القديم ويتجاهلها (JSON يتجاهل المجهول)، ويستخدمها الجديد:
- `parent_appointment_id`: `null` للأب، id الأب للابن.
- `group_root_id` / `is_child_booking`: لتحديد الجذر والانتماء دون تتبع `parent` المتسلسل.
- `group_total_amount`: مجموع المجموعة (الفاتورة الموحدة) حتى لو كانت بطاقة الأب تعرض جزئيًا.
- `linked_appointments`: مصفوفة الأبناء (أو ملخصها) داخل استجابة الأب، فيرى الجديد المجموعة كاملة من طلب واحد.
أما القوائم (`GET /api/bookings` و`GET /api/appointments`) فترجع كل صف (أب وابن) كعنصر مستقل — أي أن التقويم/القطاعات تنفصل تلقائيًا دون منطق تجميع في العميل.

**التأثير على النظام:**

| الطبقة | التأثير |
|---|---|
| `AppointmentResource.php` | إضافة ~5 حقول `whenLoaded`/`when` — تغيير صغير، لا حذف ولا إعادة تسمية. |
| `BookingController::store` | يرجع الأب محملًا بعلاقة `children` (eager) بدل صف وحيد — سطر أو سطران. |
| `GET` القوائم | بلا تغيير كود: كل صف يظهر كبطاقة — وهو المطلوب (بطاقتان). فقط التوثيق يوضح أن عناصر نفس `group_root_id` مترابطة. |
| الموبايل القديم | يعمل: يعرض بطاقة الأب فقط (الصباح) ويتجاهل الحقول الجديدة — العصر مخفي عنه حتى يُحدث (مقبول مؤقتًا، ويُذكر في ملاحظات الإصدار). |
| الموبايل الجديد | يعرض شارة «جزء 1 من 2» + رابط للكتلة الشقيقة عبر `linked_appointments`. |
| الاختبارات | اختبار عقد: نسخة قديمة (تتجاهل الحقول الجديدة) + نسخة جديدة (تقرأ المجموعة كاملة من استجابة واحدة). |

**مثال (طلب العميل نفسه بعد الإصلاح):**
```json
POST /api/bookings
{ "date": "2026-09-15", "services": [
  {"service_id": 11, "provider_id": 5, "start_time": "09:40"},
  {"service_id": 7,  "provider_id": 5, "start_time": "15:10"} ] }
// → 201
{ "success": true, "data": {
  "id": 101, "number": "APT-20260915-X1", "start_time": "09:40", "end_time": "10:00",
  "parent_appointment_id": null, "group_root_id": 101, "is_child_booking": false,
  "group_total_amount": 46.00,
  "services_details": [{"service_name": "Beard Trim & Shape", "price": 18.00}],
  "linked_appointments": [
    {"id": 102, "number": "APT-20260915-X2", "start_time": "15:10", "end_time": "15:45",
     "parent_appointment_id": 101, "group_root_id": 101, "is_child_booking": true,
     "services_details": [{"service_name": "Men's Haircut", "price": 28.00}]} ] } }
```
التطبيق القديم يقرأ `start_time/end_time/services_details` للأب فقط ويعمل. الجديد يقرأ `linked_appointments` ويعرض بطاقتين مرتبطتين.

### الخيار 2 — مصفوفة مواعيد

**النص حرفيًا:**
> يُصبح مصفوفة من المواعيد أنظف شكلًا لكنه يكسر التطبيق الحالي حتى يُحدث `data`.

**الشرح المفصل:**
تتغير `data` من كائن إلى مصفوفة `[father, child]` — أنظفRESTيًا (الطلب أنتج موردين فيُرجع موردين)، لكنه **كسر عقد صلب**: كل سطر في كل نسخة منشورة يفعل `response.data.id` سينفجر (`Array has no id`). لا يوجد مسار هجرة تدريجي — يجب نشر باك-إند وموبايل معًا في نفس النافذة، وأي عميل قديم (لم يُحدث) يتعطل كليًا لا جزئيًا (عكس الخيار 1 حيث يتعطل جزئيًا: يرى الصباح فقط).

**التأثير:** `BookingController::store` + كل عقود `API.md` + كل اختبارات العقود + نسخة API جديدة (`/v2`) أو إجبار تحديث التطبيق — تكلفة تنسيق إصدارات عالية مقابل "نظافة" شكلية. يُقبل فقط لو كان المشروع سيُصدِر `v2` قريبًا لسبب آخر.

**مثال:** نفس الطلب يرجع `"data": [{...09:40...}, {...15:10...}]` — التطبيق القديم (`data.id`) → crash/null.

### الخيار 3 — Other
مفتوح (مثلًا: إرجاع كائن `booking_group` جديد يغلف الأب والأبناء — نظيف لكنه كسر أيضًا ويحتاج `v2`).

**التوصية للسؤال 1: الخيار 1.** التوافق الخلفي ليس رفاهية هنا — التطبيق منشور بيد عملاء حقيقيين (صاحب البلاغ واحد منهم). حقول مضافة + قوائم منفصلة = إصلاح بلا إجبار تحديث.

## السؤال 2 — البيانات القديمة: كيف نعالج الصفوف الفاسدة على الإنتاج؟

**نص السؤال حرفيًا:**
> كيف نعالجها؟ (مثل الصفوف الفاسدة الموجودة على الإنتاج `APT-20260912-EDB6F2`)

**لماذا يُسأل؟**
منع التكرار (أسئلة الدفعة الأولى) لا يصلح الماضي. على الإنتاج توجد صفوف بنفس العيب (`span ≫ duration`، مثال `APT-20260912-EDB6F2`) ما زالت تحجب تقاويم المزودين كل يوم حتى تُفكك أو تُلغى. اللمس المباشر لبيانات دفع/فواتير خطر — فيلزم مسار آمن وقابل للمراجعة.

### الخيار 1 — أمر `artisan` بـ `dry-run` (Recommended)

**النص حرفيًا:**
> أمر `artisan` بـ `dry-run`: افتراضيًا يعرض الصفوف المشتبهة وماذا سيفعل بها دون أي كتابة، ومع `apply-` يقسمها فعليًا (`bookings:split-gapped` مع ... الإنشاء. المدفوع والمكتمل لا يُقاس (موسومة فقط ...)).

**الشرح المفصل (بعد إكمال النص المقطوع بما يقتضيه التصميم الآمن):**
أمر جديد `php artisan bookings:split-gapped` بوضعين:
- **الافتراضي (dry-run):** قراءة فقط — يسرد المرشحين (`span - duration > tolerance`، مثال 15 دقيقة) مع خطة كل صف (أين سينقسم، ما الكتل الناتجة، ما الفاتورة الجديدة) دون أي `INSERT/UPDATE`. المخرجات تُراجع مع الإدارة قبل أي كتابة.
- **مع `--apply`:** ينفذ نفس الخطة داخل `DB::transaction` لكل مجموعة، **بنفس منطق الإنشاء الجديد** (نفس التقسيم + نفس الفحوص + `rebuildAggregatedInvoice`)، لا منطق خاص بالترحيل — فيستحيل أن ينتج الترحيل ما يرفضه الإنشاء.
- **قاعدة السلامة المالية:** الصفوف `PENDING + فاتورة DRAFT` فقط هي القابلة للتقسيم. أي صف مدفوع/منهاة فاتورته (`PAID`) أو مكتمل (`COMPLETED`) **لا يُلمس** — يُوسم في التقرير فقط (`FLAGGED_PAID_COMPLETED`) ويُعالج يدويًا (استرداد/تسوية)، لأن تقسيمه يعيد كتابة فاتورة صادرة — خطر محاسبي وقانوني (تسلسل `INV-...` في `MON-03`).

**التأثير على النظام:**

| البند | التفصيل |
|---|---|
| كود جديد | أمر واحد + `SplitPreviewService` (يفصل المعاينة عن التنفيذ ليتشاركا نفس الحساب). |
| سلامة التشغيل | `dry-run` افتراضي = لا مفاجآت؛ `--apply` صريح + `confirm` تفاعلي + سجل `Log` لكل مجموعة (قبل/بعد). |
| الفواتير | إعادة بناء المسودات فقط عبر المسار الموحد (`rebuildAggregatedInvoice`) — لا أرقام فواتير جديدة لمدفوعات قائمة. |
| الاختبارات | `tests/Feature/Booking/SplitGappedCommandTest.php`: صف صباح+عصر PENDING → صفان + فاتورة موحدة صحيحة؛ صف PAID → مُوسوم وغير ملموس؛ `dry-run` لا يكتب شيئًا (assert `DB count` ثابت). |

**مثال:**
```
$ php artisan bookings:split-gapped
[DRAFT] APT-20260912-EDB6F2 | provider 5 | 2026-09-15 09:40–15:10 (span 330, dur 55, phantom 275)
  → SPLIT INTO: [09:40–10:00 Beard 18€] + [15:10–15:45 Haircut 28€], invoice rebuild 46€ (DRAFT stays DRAFT)
[SKIP-PAID] APT-20260910-QQ11 | already PAID → flagged only, manual review
0 written (dry-run). Re-run with --apply to execute.

$ php artisan bookings:split-gapped --apply
✔ 1 group split, 1 flagged. Log: storage/logs/split-gapped-2026-09-25.log
```

### الخيار 2 — كشف فقط

**النص حرفيًا:**
> أمر يكتفي بسرد الصفوف المشتبهة، والإصلاح يدوي بدون اللوحة (إلغاء وإعادة حجز).

**الشرح المفصل:**
نفس الكشف لكن دون تنفيذ آلي أبدًا. كل صف يُصلح يدويًا من اللوحة: إلغاء (`ADMIN_CANCELLED`) + إعادة حجز كتلتين + إشعار العميل. آمن ماليًا (لا كود يلمس الفواتير)، لكنه **لا يتوسع**: صف واحد (حالة العميل) مقبول يدويًا؛ عشرات الصفوف = ساعات عمل موظفين + أخطاء إدخال + إزعاج عملاء (إلغاءات تظهر في سجلهم + إيميلات إلغاء كاذبة) + خطر ضياع الفتحة بين الإلغاء وإعادة الحجز (شخص آخر يحجز العصر في هذه الثواني — نفس ثقب `BOOK-02` لكن بشريًا).

**مثال:** قائمة 12 صفًا مشتبهًا → 12 مكالمة عميل + 24 حجزًا يدويًا + 12 فاتورة مسودة تُبنى يدويًا — يوم عمل كامل لفريق الاستقبال.

### الخيار 3 — لا شيء

**النص حرفيًا:**
> المهمة تمنع التكرار فقط، وأنت تعالج الصف المبلغ عنه يدويًا.

**الشرح المفصل:**
يُترك كل الإنتاج الفاسد كما هو عدا الصف المُبلغ عنه. النتيجة: التقاويم تبقى محجوبة كذبًا لأسابيع (حتى تنتهي تواريخها)، `409` كاذبة مستمرة، تقارير الإشغال مضخمة، وثقة المزودين ("يومي محجوز وهو فارغ") تتآكل — بينما نعلن أن المشكلة "أُصلحت". دين تقني يتحول لدين تشغيلي يومي.

**مثال:** صف فاسد بتاريخ 2026-10-20 سيحجب 5 ساعات في ذلك اليوم حتى بعد نشر الإصلاح — والعميل الثاني الذي يُرفض في الفجوة لن يعرف أن السبب صف قديم.

### الخيار 4 — Other
مفتوح (مثلًا: تقسيم آلي مجدول `queue` ليلًا — مرفوض: كتابة مالية آلية بلا مراجعة بشرية).

**التوصية للسؤال 2: الخيار 1.** المعاينة الآمنة + التنفيذ الصريح + حماية المدفوع = التوازن الوحيد بين السرعة والسلامة المالية. الخيار 2 احتياطي مقبول فقط إذا كان عدد الصفوف < 5 فعلًا (يُعرف من `dry-run` نفسه).

## السؤال 3 — الآثار الجانبية للتقسيم: ما المشمول في المهمة؟ (اختيار متعدد)

**نص السؤال حرفيًا:**
> الآثار الجانبية للتقسيم: أيها تريد معالجته ضمن المهمة؟

**لماذا يُسأل؟**
التقسيم يضاعف عدد الصفوف لكل طلب متباعد، وكل عدّاد في النظام كان يفترض "طلب = صف" سينحرف ما لم يُحدّث. البنود الأربعة أدناه ليست زينة — كل واحد متروكًا سيُنتج bug جديدًا بقدر المشكلة الأصلية. (تظهر في الواجهة كـ checkboxes — اختر كل ما يشمله النطاق.)

### البند 1 — الحد اليومي بعد المجموعة

**النص حرفيًا:**
> يُعدّ المجموعات (الجذور) لا الصفوف. كحجز واحد مقسوم. فحجز واحد = ... `validateDailyBookingLimit`

**الشرح المفصل:**
`BookingValidationService::validateDailyBookingLimit()` في `app/Services/BookingValidationService.php:406` يعدّ اليوم `where(customer_id).whereDate(...).where(status PENDING)->count()` مقابل `max_daily_bookings` (افتراضي 10). بعد التقسيم طلب واحد متباعد = صفان → يُحتسب حجزان. العميل الذي حجز صباح+عصر (طلب واحد!) يستهلك ضعف حصته — عقاب على التقسيم التقني الذي لم يختره.

**التأثير (مشمول):** تغيير العدّ إلى الجذور: `whereNull(parent_appointment_id)` (الأب/المستقل فقط) أو `group_root_id` المميز. تغيير سطرين + اختبار: طلب بكتلتين → العدّ +1 لا +2. **إن تُرك:** شكاوى "وصلت للحد اليومي بحجز واحد!".

**مثال:** `max_daily_bookings = 3`. عميل يحجز صباح+عصر (مجموعة واحدة) ثم حجزان منفصلان آخران = 4 صفوف. بالعدّ الخاطئ (صفوف): 4 ≥ 3 → **مرفوض** ظلمًا. بالعدّ الصحيح (جذور): 3 مجموعات = الحد تمامًا → **مقبول**.

### البند 2 — تنبيه الإلغاء بعد المجموعة

**النص حرفيًا:**
> يُعدّ المجموعات الملغاة، فإلغاء حجز من كتلتين لا يطلق تنبيهًا للمدير وحده `CancellationMonitor`.

**الشرح المفصل:**
`CancellationMonitor::recordCustomerCancellation()` في `app/Services/CancellationMonitor.php:43` يعدّ `USER_CANCELLED` خلال 7 أيام، والعتبة 2 (من الإلغاء الثاني تنبيه لكل `admin/manager` — `BOOK-08`). إلغاء مجموعة من كتلتين (إلغاء الأب ثم الابن، أو إلغاء جماعي) = حدثان → **تنبيه كاذب** "عميل كثير الإلغاء" من أول حجز حقيقي واحد. الأسوأ: مع خيار "إلغاء الأب يلغي الجميع" (المرفوض في الدفعة الأولى) يتضخم أكثر.

**التأثير (مشمول):** العدّ على مستوى المجموعة: إلغاء كل كتل مجموعة واحدة خلال نافذة قصيرة (نفس العملية/اليوم) = 1 في العدّ، أو تمرير `group_root_id` للمراقب لخصم التكرار. تغيير متوسط + اختبار: إلغاء كتلتين لنفس المجموعة → لا تنبيه؛ إلغاء مجموعتين مختلفتين → تنبيه. **إن تُرك:** مدراء يتلقون تنبيهات كاذبة ويفقدون الثقة بالتنبيهات (تنبيه-تعب).

**مثال:** عميل ألغى صباح+عصر (مجموعة واحدة) يوم الاثنين. بالعدّ الخاطئ: `count = 2 ≥ 2` → **تنبيه للإدارة** رغم أنه إلغاء واحد منطقيًا. بالصحيح: `count = 1` → صمت.

### البند 3 — تذكير لكل كتلة

**النص حرفيًا:**
> يُجدول لكل كتلة (صباحًا وعصرًا) لا للأولى فقط `reminder_offset_hours`.

**الشرح المفصل:**
`BookingController::store` يستخرج `reminder_offset_hours` (من `BookingCreateRequest.php:54`) ويجدول تذكيرًا واحدًا عبر `AppointmentReminderService` محسوبًا من `start_time` (`remindAtFromOffset`). القيد: موعد واحد = تذكير حي واحد (`activeReminder` + فهرس `one_active`). بعد التقسيم: التذكير الواحد سيُجدول لكتلة الأب فقط — **كتلة العصر بلا تذكير** → `NO_SHOW` مسائي مؤكد تقريبًا. وكل كتلة صف مستقل فيستطيع حمل تذكيره الخاص دون كسر القيد (واحد لكل صف، اثنان للمجموعة — مسموح).

**التأثير (مشمول):** حلقة جدولة لكل صف في المجموعة بنفس الـ offset (تذكير الصباح قبل الصباح بساعتين، والعصر قبل العصر بساعتين)، وإلغاء التذكيرين عند إلغاء المجموعة (الـ `updated` hook في `Appointment.php:122` يغطي كل صف على حدة — يعمل تلقائيًا). تغيير صغير في `scheduleReminderForBooking` + اختبار: مجموعة كتلتين + offset=2 → تذكيران حيّان بأوقات صحيحة. **إن تُرك:** نصف المواعيد المقسمة بلا تذكير — إصلاح يخلق `NO_SHOW`.

**مثال:** حجز صباح 09:40 + عصر 15:10 مع `reminder_offset_hours = 2`. الصحيح: تذكيران (07:40 + 13:10). الخاطئ (الأولى فقط): تذكير 07:40 وحده — العميل ينسى العصر.

### البند 4 — إيميل واحد يسرد كل الكتل

**النص حرفيًا:**
> لصف واحد `time_range` إيميل التأكيد (للعميل وللصالون) يعرض كل كتلة بتوقتها وخدماتها والمجموع الكلي، بدل ...

**الشرح المفصل:**
`BookingMailService::sendForNewBooking()` في `app/Services/BookingMailService.php:28` يرسل إيميلين (تأكيد العميل للحجوزات `ONLINE` + إشعار الشركة لكل حجز) مبنيين على صف واحد (`$appointment->time_range` + خدماته). بعد التقسيم إيميل الأب وحده سيعرض "09:40–10:00، 18€" ويخفي العصر (28€) — العميل يظن أن حجزه صباح فقط ويتصل "أين موعد العصر؟"، والصالون يرى نصف الحجز في بريده.

**التأثير (مشمول):** تمرير المجموعة كاملة (`$appointment->load(children.services_record)`) للقالبين (`BookingConfirmationMail` + `BookingNotificationMail`) وعرض جدول كتل (وقت كل كتلة + خدماتها + مزودها) + المجموع الكلي، مع إبقاء الإرسال مرة واحدة (إيميل واحد لا إيميلين — تجنب السبام). تغيير قوالب + اختبار لقطة (snapshot) للإيميل. **إن تُرك:** الإصلاح التقني يبدو مكسورًا في بريد العميل — أسوأ أنواع الـ bugs (صحيح في DB، خاطئ في عين المستخدم).

**مثال (قبل/بعد):**
- قبل (خاطئ): «موعدك 09:40–10:00، Beard Trim، 18€» — أين الـ 28€ والعصر؟
- بعد (صحيح): «حجزك من كتلتين: ① 09:40–10:00 Beard (Aisha) ② 15:10–15:45 Haircut (Aisha) — المجموع 46€، فاتورة واحدة تُدفع مرة واحدة».

**التوصية للسؤال 3: شمول البنود الأربعة كلها ضمن المهمة.** كل واحد سطرون–عشرون سطرًا، وترك أي منها يزرع bug جديدًا مؤكدًا (حد ظالم / تنبيه كاذب / عصر بلا تذكير / إيميل ناقص). لا يُؤجل أي بند إلا الإيميل كحد أقصى — والتأجيل مرفوض هنا لأنه واجهة العميل المباشرة.

## السؤال 4 — تطبيق الموبايل ليس في هذا المستودع. ما المطلوب بخصوصه؟

**نص السؤال حرفيًا:**
> تطبيق الموبايل ليس في هذا المستودع. ما المطلوب بخصوصه؟

**لماذا يُسأل؟**
هذا المستودع (`BarberBooking` باك-إند + داشبورد) لا يحوي كود الموبايل (الفريق منفصل، الصورة الأولى `Meine Termine` من مستودع آخر). القرار: هل نكتفي بتوثيق العقد ليبنيه فريق الموبايل، أم نطلب مسار مستودعهم ونعدّله هنا؟ الخلط بين المستودعين هو مصدر تأخير شائع — يُحسم الآن.

### الخيار 1 — بالـ `API.md` + توثيق للموبايل (Recommended)

**النص حرفيًا:**
> بالـ `API.md` + توثيق للموبايل: وأكتب قسمًا للفريق الموبايل بالحقول الجديدة (اختياري): إظهار شارة «جزء من حجز» منذ ... `API.md` منذ التالب-إند واللوحة وأُحدث — التطبيق الحالي يعمل دون تحديث.

**الشرح المفصل (بعد إكمال المقطوع):**
النطاق = هذا المستودع فقط: تحديث `API.md` (عقد `POST/GET /bookings`: الحقول الخمسة الجديدة + قاعدة "القوائم ترجع الكتل منفصلة" + أمثلة JSON قبل/بعد) + قسم «تعليمات فريق الموبايل» (كيف يعرض بطاقتين مرتبطتين + شارة «جزء 1 من 2» **اختيارية** في النسخة الجديدة، لا إجبارية). الباك-إند (الخيار 1 في سؤال العقد) يضمن أن **التطبيق الحالي يعمل دون تحديث** (يعرض الأب فقط) — فلا استعجال ولا نشر متزامن.

**التأثير:** ملف توثيق فقط + لا كود موبايل هنا + لا تنسيق نشر مشترك. فريق الموبايل يقرأ وينفذ بسرعته. الاختبار: عقد `AppointmentResource` (الحقول الجديدة موجودة ومهملة بأمان من القديم).

**مثال (مقتطف `API.md` الجديد):**
```md
### Grouped bookings (multi-block)
- `POST /api/bookings` returns the ROOT appointment; its `linked_appointments[]` holds the other blocks.
- `GET /api/bookings` returns every block as its own item; group via `group_root_id`.
- Old clients: ignore unknown fields — the root card keeps working.
- New clients (optional): show badge "Teil 1 von 2" and link siblings.
```

### الخيار 2 — لاحق كود التطبيق

**النص حرفيًا:**
> لاحق كود التطبيق (سأعطيك مسار مشروع الموبايل لتعديله أيضًا (اكتب المسار في `Other`).

**الشرح المفصل:**
توسيع النطاق ليشمل مستودع الموبايل (Flutter/React-Native — غير معروف هنا): تعديل شاشة `Meine Termine` (عرض بطاقتين + شارة + إلغاء فردي) واختبارها على أجهزة. يتطلب: مسار المستودع + بيئة بنائه + حسابات متاجر النشر + تنسيق إصدار متزامن مع الباك-إند — أي مشروع ثانٍ كامل داخل هذه المهمة، بفريق ومراجعات مختلفة.

**التأثير:** تضخيم النطاق ×2–3، وربط نشر الباك-إند (يمكن نشره اليوم بتوافق خلفي) بنشر الموبايل (دورة مراجعة متجر أيام). **يُقبل فقط** إذا كان فريق واحد يملك المستودعين معًا وبيئة الموبايل جاهزة — وهو غير ثابت هنا ("ليس في هذا المستودع").

**مثال:** `Other: D:\Coding\BarberApp (Flutter)` + تعديل `lib/screens/appointments/my_terms.dart` لعرض `linked_appointments` — مهمة منفصلة بمراجعة منفصلة.
