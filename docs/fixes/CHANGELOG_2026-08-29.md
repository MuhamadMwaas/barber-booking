## 2. AUTH-01 — حدود المعدّل على نقاط المصادقة

### المشكلة

تسعة مسارات مصادقة كانت **بلا أي سقف**: `login`, `register`, `refresh`, `request-otp`, `verify-otp`, `verify-email-otp`, `resend-verification-otp`, `google`, `google/mobile`.

يعني: مهاجم يستطيع تجريب مليون كلمة مرور، أو مليون رمز OTP، بسرعة الشبكة فقط.

---

### التعديل ١ — `config/rate_limits.php` (جديد)

**ماذا:** ملف إعدادات فيه كل الأرقام.

```php
'login' => [
    'per_ip'           => 10,   // طلبات/دقيقة من نفس العنوان
    'per_account'      => 5,    // طلبات/دقيقة على نفس الحساب
    'per_account_hour' => 20,   // طلبات/ساعة على نفس الحساب
],
'otp_verify' => [
    'per_ip'               => 10,
    'per_destination'      => 5,
    'per_destination_hour' => 20,
],
// ... register / refresh / otp_send / social
```

**لماذا:** الأرقام تحتاج ضبطاً بعد الإطلاق حسب سلوك عملائك الحقيقي. وضعها في ملف إعداد يعني أنك تضبطها من `.env` بلا لمس الكود ولا إعادة نشر.

**الأثر:** تستطيع تخفيف أي حدّ فوراً إن اشتكى عميل:
```env
RL_LOGIN_PER_ACCOUNT=10
```

---

### التعديل ٢ — `app/Support/ThrottleKey.php` (جديد)

**ماذا:** كلاس صغير يقرأ من جسم الطلب: «أي حساب يستهدفه هذا الطلب؟» ويُرجع مفتاحاً مُطبَّعاً ومجزّأً.

**لماذا — وهذه أهم فكرة في الإصلاح كله:**

الحدّ التقليدي `throttle:5,1` يُفرَض على **عنوان الـ IP**. لكن:

> **المهاجم يختار عنوانه. وما لا يختاره أبداً هو الحساب الذي يهاجمه.**

فلو اكتفينا بالـ IP، يكفي المهاجم أن يبدّل عنوانه كل 5 طلبات ليتجاوز كل شيء. لذلك نحتاج بُعداً ثانياً: **الحساب المستهدَف**. وهذا الكلاس هو من يستخرجه.

**ثلاثة قرارات داخله:**

| القرار | لماذا |
|---|---|
| تطبيع البريد إلى أحرف صغيرة | بدونه `Victim@X.com` و`victim@x.com` دلوان منفصلان → الحدّ يتضاعف بتغيير حالة الأحرف |
| تطبيع الهاتف (أرقام + `+` فقط) | `+49 30 123` و`+49-30-123` نفس الرقم، يجب أن يكونا نفس الدلو |
| لا يرمي استثناءً أبداً | `email[]=x` (مصفوفة) كان سيسبب `TypeError` = **500 على نقطة غير مصادَق عليها** |

**الأثر:** الحماية تصمد أمام مهاجم يبدّل عناوينه — وهذا ما تحقّق فعلياً في الاختبار (القسم 5).

---

### التعديل ٣ — `app/Providers/AppServiceProvider.php`

**ماذا:** أُضيفت دالة `registerAuthRateLimiters()` تُعرّف 6 محدِّدات مُسمّاة.

```php
RateLimiter::for('auth-login', function (Request $request) {
    return [
        Limit::perMinute(10)->by('auth-login:ip:' . $request->ip()),          // بُعد العنوان
        Limit::perMinute(5)->by($accountKey($request, 'auth-login')),          // بُعد الحساب
        Limit::perHour(20)->by($accountKey($request, 'auth-login-hourly')),    // حاجز طويل المدى
    ];
});
```

**لماذا محدِّدات مُسمّاة لا `throttle:5,1` المضمّنة؟**

لأن الصياغة المضمّنة **لا تستطيع التعبير عن بُعدين**. تكتب رقماً واحداً ونافذة واحدة، والمفتاح دائماً الـ IP. وهذا بالضبط ما لا يكفي.

**تفصيلتان صغيرتان تمنعان عللاً صامتة:**

**أ) كل مفتاح مسبوق باسم المحدِّد**
```php
->by('auth-login:ip:' . $request->ip())   // ✅
->by($request->ip())                       // ❌ كان سيشارك الدلو
```
دلاء المحدِّدات مشتركة على مستوى الكاش كله. مفتاح غير مسبوق كان سيجعل طلب `login` **يُنفق ميزانية `verify-otp`** لنفس العنوان.

**ب) السقوط الآمن إلى الـ IP**
```php
return $identifier !== null
    ? "{$scope}:acct:{$identifier}"
    : "{$scope}:ip:{$request->ip()}";      // ✅ لا مسار بلا حدّ
```
بدونه، مهاجم يحذف حقل `email` من الطلب فيحصل على مفتاح فارغ = **مسار غير محدود**.

**الأثر:** حماية ثنائية البُعد لا يتجاوزها تبديل العناوين.

### التعديل ٤ — `routes/api.php`

**ماذا:** أُضيف `->middleware('throttle:...')` لتسعة مسارات.

```php
Route::post('login', [AuthController::class, 'login'])
    ->middleware('throttle:auth-login');

Route::post('verify-otp', [OtpController::class, 'verifyOtp'])
    ->middleware('throttle:otp-verify');
// ... إلخ
```

**نقطة كانت ستُفوَّت بسهولة:** `verify-email-otp` لا يحتوي منطقاً خاصاً به — بل يُفوِّض مباشرة إلى `verifyOtp()`:

```php
public function verifyEmailViaOtp(Request $request)
{
    $request->merge(['registration_method' => 'email']);
    return $this->verifyOtp($request);       // نفس سطح التخمين، باسم آخر
}
```

تركه بلا حدّ كان سيترك **باباً ثانياً غير مُقاس إلى نفس الهجوم**. الآن يحمل نفس المحدِّد ويتقاسم نفس الميزانية.

**استثناءان مقصودان:** `logout` (مصادَق عليه أصلاً) و`google/redirect|callback` (تحويلات ويب، يغطّيها `throttle:api`).

**الأثر:** كل نقطة مصادقة محمية، ولا باب خلفي.

### التعديل ٥ — ملفات اللغة الثلاث

**ماذا:** أُضيف مفتاح `auth.throttle_generic` بالعربية والألمانية والإنجليزية. وصُحِّح `lang/ar/auth.php` سطر 6 (كان نصاً إنجليزياً في ملف عربي).

**لماذا:** استجابة Laravel القياسية عند تجاوز الحدّ هي:
```json
{"message": "Too Many Attempts."}
```
بالإنجليزية فقط، وبلا `success` ولا `error_type`. تطبيق الموبايل يقرأ `success`/`message` فلن يعرض شيئاً مفهوماً. الآن:
```json
{
  "success": false,
  "message": "طلبات كثيرة جداً. يرجى المحاولة مجدداً بعد 60 ثانية.",
  "error_type": "rate_limited",
  "retry_after": 60
}
```

**ونقطة أمنية في صياغة الرسالة:** لا تذكر **أي** حدّ تم تجاوزه. لو قالت «تجاوزت حدّ هذا الحساب» لكانت **أكّدت للمهاجم أن الحساب موجود** — أي حوّلت حماية إلى أداة تعداد مستخدمين.

**الأثر:** التطبيق يعرض رسالة صحيحة بلغة العميل، ويعرف متى يُعيد المحاولة.

### التعديل ٦ — `LoginRequest.php` و`RegisterRequest.php`

**ماذا:**
```php
// قبل
'registration_method' => strtolower((string) $this->input('registration_method')),

// بعد
$method = $this->input('registration_method');
if (is_string($method)) {
    $this->merge(['registration_method' => strtolower($method)]);
}
```

**لماذا:** `registration_method[]=email` يجعل `input()` يُرجع مصفوفة، وتحويل مصفوفة إلى نص يرفع `Array to string conversion` التي يحوّلها Laravel إلى استثناء → **500 على نقطة غير مصادَق عليها**.

**🔸 هذا إصلاح خارج نطاق AUTH-01 — وأُعلنه صراحةً.** العلة **كانت موجودة قبل عملي** وأثبتُّ ذلك:

```
ThrottleKey::forIdentifier()          → OK  (كودي تعامل مع المصفوفة صحيحاً)
LoginRequest::prepareForValidation()  → THREW ErrorException
                                         at app/Http/Requests/LoginRequest.php:46
```

أصلحتُها لأنها على المسارات نفسها التي كنتُ أُحصّنها، والإصلاح ثلاثة أسطر. **تراجُعها سهل إن أردت تتبّعها كبند منفصل:**
```bash
git checkout app/Http/Requests/LoginRequest.php app/Http/Requests/RegisterRequest.php
```

**الأثر:** المدخل المشوّه يُرجع `422` بدل `500`.

## 3. AUTH-02 — حدّ محاولات الـ OTP

### المشكلة

```php
if ($record->attempts >= $maxAttempts) {   // (1) فحص على قيمة قُرئت سابقاً
    // رفض
}
if (!hash_equals($record->otp, $otp)) {
    $record->increment('attempts');         // (2) كتابة — لا شيء يربطها بالفحص
}
```

الفحص والكتابة منفصلان. عند وصول طلبات متزامنة، **كلها تقرأ `attempts = 0` وكلها تجتاز الفحص**.

**تصحيح على ما كتبتُه في التقرير الأمني:** قلتُ إن «العدّاد يتخلّف» — وهذا **خطأ**. `increment()` يُصدر `SET attempts = attempts + 1` وهو ذرّي، والعدّاد دقيق دائماً. المشكلة في **الفحص** لا في الزيادة. والتمييز مهم لأنه غيّر الحل.

---

### التعديل ٧ — `app/Services/OtpService.php`

**ماذا:** أُعيدت كتابة `validate()` وأُضيفت دالتان.

```php
protected function claimAttempt(int $otpId, int $maxAttempts): bool
{
    return Otp::query()
        ->whereKey($otpId)
        ->where('attempts', '<', $maxAttempts)   // ← الحارس داخل الاستعلام
        ->where('used', false)
        ->where('expires_at', '>', now())
        ->update(['attempts' => DB::raw('attempts + 1')]) === 1;
}
```

**الفكرة:** انقل الحارس إلى داخل `WHERE`. الآن **قاعدة البيانات** — لا PHP — هي من تُقرّر إن كانت هناك فتحة متاحة، وتُقرّر لمستدعٍ واحد في كل مرة.

عدد الصفوف المتأثرة هو الجواب:
- `1` → هذا الطلب يملك محاولة، ويجوز له تقييم تخمينه
- `0` → الحدّ مستنفَد → ارحل قبل الوصول إلى المقارنة

**لماذا لم أستخدم `lockForUpdate` (وهو ما اقترحتُه في التقرير)؟**

لأن `generate()` يعمل داخل معاملة ويُنفّذ `invalidateUnusedOtps()` = `UPDATE otps SET used=1 WHERE email=?` على **نفس الصفوف**. لو أمسك `validate()` قفلاً صفّياً، فإن عميلاً يضغط **«إعادة إرسال» أثناء تحقق جارٍ** → معاملتان تتنافسان → **deadlock → 500**.

| | `lockForUpdate` | UPDATE شرطية |
|---|---|---|
| معاملة مطلوبة | نعم | **لا** |
| خطر deadlock | **نعم** | لا |
| عدد الاستعلامات | 3+ | **1** |
| نفس الضمان | ✅ | ✅ |

**وسباق ثانٍ أُغلق بالمناسبة:**
```php
protected function burn(int $otpId): bool
{
    return Otp::query()->whereKey($otpId)
        ->where('used', false)              // ← الحارس
        ->update(['used' => true]) === 1;
}
```
في الكود القديم، طلبان متزامنان بالرمز **الصحيح** كانا **كلاهما ينجحان**. الآن الاستهلاك مرة واحدة فعلاً — وهذا جوهري لأن نجاح التحقق يُستبدَل بسلطة حقيقية (منحة إعادة تعيين كلمة مرور، حساب موثَّق).

**التوقيع لم يتغيّر** — المستدعون الثلاثة يعملون بلا أي تعديل:
`OtpController:80` · `PhoneVerificationController:141` · `PasswordResetService:83`

**الأثر:** لا يمكن تقييم أكثر من 5 تخمينات لأي رمز، مهما بلغ التوازي.

### التعديل ٨ — الميجريشن الجديد

**ماذا:**
```sql
ALTER TABLE `otps` MODIFY `expires_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
```

**لماذا — وهذه علة اكتشفتُها أثناء العمل ولم تكن في التقرير أصلاً:**

الميجريشن الأصلي كتب:
```php
$table->timestamp('expires_at');     // بلا nullable، بلا default
```

سيرفرك يعمل بـ `explicit_defaults_for_timestamp = OFF` (تحققتُ). وفي هذا الوضع، **MySQL يُلحق تلقائياً** بأول عمود `TIMESTAMP NOT NULL`:
```
DEFAULT CURRENT_TIMESTAMP  و  ON UPDATE CURRENT_TIMESTAMP
```

**لا شيء في ميجريشن Laravel يقول ذلك — قاعدة البيانات هي من أضافته.** ولهذا مرّ دون ملاحظة.

**النتيجة على عملائك:**

```
انشئ         : expires_at = 18:44:18   (بعد 10 دقائق)
خطأ مطبعي #1 : attempts = 1
               expires_at = 18:34:18   ← قفز إلى "الآن"
الرمز الصحيح : مرفوض                   ← العميل عالق
```

**أي عميل يُخطئ رقماً واحداً يفقد رمزه** ويجب أن ينتظر 60 ثانية ويطلب رمزاً جديداً. في التسجيل، وإعادة تعيين كلمة المرور، وتحقق الهاتف.

**لماذا كان لا بد من إصلاحها هنا؟** لأنها **شرط مسبق لا توسيع نطاق**: أي إصلاح لـ AUTH-02 يزيد العدّاد كان سيُصيّر الرمز منتهياً في نفس الكتابة — فيبدو الحدّ ناجحاً بينما الرمز مُدمَّر. كنتُ سأشحن «إصلاحاً» يُخفي عطلاً تحت مظهر الأمان.

**لماذا SQL خام لا `->change()`؟** لأن `$table->timestamp('expires_at')->change()` يُعيد إصدار `TIMESTAMP NOT NULL` مجرّداً، فتُطلَق قاعدة MySQL نفسها ويعود `ON UPDATE`. تسمية `DEFAULT` صراحةً هي ما يُلغي الإسناد التلقائي.

**الأثر:** الخطأ المطبعي لم يعد يُبطل الرمز.

## 5. الأثر — بالأرقام الفعلية

كل ما يلي مخرجات حقيقية من تشغيل على مشروعك، لا استنتاج.

### أ) الحدّ يصمد أمام تبديل العناوين

```
حساب ضحية واحد، كل طلب من IP مختلف:
  IP 198.51.100.1 -> 401       IP 198.51.100.5 -> 401
  IP 198.51.100.2 -> 401       IP 198.51.100.6 -> 429  ← أُوقف
  IP 198.51.100.3 -> 401       IP 198.51.100.7 -> 429
  IP 198.51.100.4 -> 401       IP 198.51.100.8 -> 429
```
`throttle:5,1` كان سيمرّر كل هذه الطلبات.

### ب) سباق الـ OTP مُغلق

```
قبل: 8 جلسات قرأت attempts=0 → 8 تخمينات مقابل حدّ 5
بعد: نفس المشابكة → 5 مُنحت، 3 مرفوضة → 5 بالضبط
```

### ج) السلوك الوظيفي

| الحالة | قبل | بعد |
|---|---|---|
| خطأ مطبعي ثم الرمز الصحيح | `false` ❌ | `true` ✅ |
| استرداد الرمز الصحيح مرتين | `true` ❌ | `false` ✅ |
| استنفاد الحدّ يحرق الرمز | ✅ | ✅ |
| رمز منتهٍ مرفوض | ✅ | ✅ |

### د) جدوى تخمين الـ OTP

```
مساحة الرمز : 1,000,000 احتمال
عمر الرمز   : 10 دقائق
الحدّ        : 20 محاولة/ساعة على الوجهة

الزمن اللازم = 1,000,000 ÷ 20 = 50,000 ساعة ≈ 5.7 سنة
```
الهجوم لم يعد صعباً — صار **مستحيلاً رياضياً**.

### هـ) المجموعة الكاملة

```
قبل هذه المهمات : 17 failed, 2 skipped, 243 passed (640 assertions)
بعدها           : 17 failed, 3 skipped, 256 passed (690 assertions)
```

**الـ17 فشلاً سابقة لعملي وغير متغيّرة.** أثبتُّ ذلك بـ `git stash` ثم تشغيل الأساس ومقارنة أسماء الاختبارات الفاشلة → `IDENTICAL`. وهي في Fiskaly وTaxCalculator وProfileImageUpload وDeleteAccount وExampleTest — ثلاثة منها مرتبطة بـ`MON-01` في التقرير الأمني.

## 6. حدود يجب أن تعرفها

### أ) الاختبارات تعمل على sqlite

`phpunit.xml` يضبط `DB_CONNECTION=sqlite`. لذلك:
- اختبار الـschema (`expires_at`) **يتخطّى** — العلة خاصة بـ MySQL.
- اختبار «خطأ ثم صحيح» **ينجح على sqlite بغض النظر عن الإصلاح** — فهو لا يحرس العلة في CI.

**الحارس الفعلي هو الميجريشن نفسه.** كل نتائج القياس أعلاه من قاعدة MySQL الحقيقية، يدوياً.

> ⚠️ **لا تُشغّل** `DB_CONNECTION=mysql php artisan test` على قاعدة التطوير — `RefreshDatabase` سيمسحها.

### ب) مقايضة الحدّ المرتبط بالحساب

مهاجم يستطيع عمداً استنفاد ميزانية دخول ضحية بـ5 محاولات خاطئة، فيمنعه من الدخول لدقيقة.

**هذه مقايضة أصيلة في كل حدّ مرتبط بحساب، لا عيب تنفيذ.** البديل — بُعد الـ IP وحده — يعني لا حماية إطلاقاً أمام مهاجم موزَّع. حرمان مؤقت أهون من استيلاء دائم. إن رأيته مزعجاً عملياً، ارفع `RL_LOGIN_PER_ACCOUNT` في `.env` بلا لمس الكود.

### ج) النقر المزدوج على «تحقق»

الرمز صار يُستهلك مرة واحدة فعلاً. لو ضغط المستخدم مرتين سريعاً بالرمز الصحيح، الطلب الأول ينجح والثاني يُرجع `false`. هذا السلوك الصحيح لسرّ يُستخدم مرة واحدة، لكن الحماية من النقر المزدوج مسؤولية تطبيق العميل.
