## 1. تصحيحان على تدقيقي الأصلي

كتبتُ `AUTH-02` في التقرير اعتماداً على **`grep` لا على قراءة كاملة** للملف. قراءة الملف كاملاً كشفت خطأين في صياغتي:

### التصحيح الأول: اسم الدالة والتوقيع

| في التقرير | الحقيقة |
|---|---|
| `public function verify(string $target, string $code, OtpPurpose $purpose)` | `public function validate(string $target, string $otp, OtpType $type = ..., OtpPurpose $purpose = ...)` |

الحل الذي اقترحتُه **لم يكن ليعمل كبديل مباشر**: اسم خاطئ، ومعامل `OtpType` مفقود بالكامل.

### التصحيح الثاني — والأهم: «العدّاد يتخلّف» وصف خاطئ

قال التقرير:

> «هجوم متوازٍ يتجاوز `maxAttempts`… العدّاد يتخلّف»

**العدّاد لا يتخلّف أبداً.** `Model::increment()` في Laravel يُصدر:

```sql
UPDATE otps SET attempts = attempts + 1 WHERE id = ?
```

وهذه عملية **ذرّية على مستوى قاعدة البيانات** — لا قراءة-تعديل-كتابة في PHP، ولا زيادة تُفقَد أبداً. وقد أثبتُّ ذلك: بعد 8 جلسات متوازية كانت `attempts = 8` **بالضبط**.

**الخلل الحقيقي في الفحص لا في الزيادة:**

```php
if ($record->attempts >= $maxAttempts) {   // يقرأ قيمة قديمة من الذاكرة
```

الفحص يعمل على نسخة قُرئت قبل أن يكتب أحد. **فحصٌ غير مندمج بالكتابة التي يحرسها ليس فحصاً.**

هذا التمييز ليس لغوياً — بل يغيّر الحل. لو كانت المشكلة في الزيادة، لكان الحل قفلاً. وبما أن المشكلة في الفحص، فالحل هو **دمج الفحص بالكتابة**، وهذا أرخص وأمتن من القفل.

## 3. الاكتشاف غير المتوقّع: علة أخطر كانت تختبئ خلف AUTH-02

أول محاولة لإثبات السباق أعطت نتيجة غريبة: `attempts = 0` رغم عشرات الطلبات. التقصّي كشف علة **أخطر يومياً من AUTH-02 نفسها**:

```
انشئ           : expires_at = 18:44:18   (بعد 10 دقائق، now = 18:34:18)
محاولة خاطئة #1: false
   بعدها       : attempts = 1
                 expires_at = 18:34:18   ← قفز إلى "الآن"!
الرمز الصحيح   : false                   ← الرمز الصحيح مرفوض
```

### السبب الجذري

```php
// database/migrations/2025_09_06_114158_create_otps_table.php:19
$table->timestamp('expires_at');        // بلا nullable، بلا default
```

في MySQL/MariaDB مع `explicit_defaults_for_timestamp = OFF` — **وهو الإعداد الفعلي على سيرفرك، تحققتُ منه**:

> أول عمود `TIMESTAMP NOT NULL` في الجدول، إن لم يُصرَّح بـ NULL أو DEFAULT أو ON UPDATE، **يُمنَح تلقائياً `DEFAULT CURRENT_TIMESTAMP` و`ON UPDATE CURRENT_TIMESTAMP`**.

لا شيء في ميجريشن Laravel يقول ذلك — **قاعدة البيانات هي من أضافته، لا الكود**. ولهذا مرّ دون ملاحظة.

```sql
-- قبل الإصلاح
COLUMN_NAME: expires_at   EXTRA: on update current_timestamp()
```

### الأثر على العملاء

أي عميل يُخطئ رقماً واحداً في رمز التحقق:
1. المحاولة الخاطئة تزيد `attempts` → قاعدة البيانات تُصيّر `expires_at = NOW()`
2. الرمز يصبح منتهياً **فوراً**
3. الرمز الصحيح بعدها **مرفوض**
4. لا خيار إلا انتظار `resend_cooldown_seconds` (60 ثانية) وطلب رمز جديد

**خطأ مطبعي واحد = دورة كاملة من 60 ثانية.** وهذا يمسّ كل عميل يسجّل، وكل إعادة تعيين كلمة مرور، وكل تحقق من رقم هاتف.

### لماذا كان لا بد من إصلاحه ضمن AUTH-02

هذا **شرط مسبق، لا توسيع نطاق**. أي إصلاح لـ AUTH-02 يزيد العدّاد سيُصيّر الرمز منتهياً في نفس الكتابة — فيبدو الحدّ وكأنه يعمل (الطلبات اللاحقة لا تجد سجلاً حيّاً) **بينما الرمز في الحقيقة مُدمَّر**. كنتُ سأشحن «إصلاحاً» يُخفي عطلاً تحت مظهر الأمان.

### مسح شامل: أربعة أعمدة أخرى مصابة بالعلة نفسها

```sql
SELECT TABLE_NAME, COLUMN_NAME, EXTRA FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND EXTRA LIKE '%on update%' AND COLUMN_NAME <> 'updated_at';
```

| الجدول.العمود | الأثر الفعلي | القرار |
|---|---|---|
| `otps.expires_at` | **ضرر نشط** — يُبطل رمز كل عميل يُخطئ | ✅ **أُصلح** (شرط مسبق) |
| `refresh_tokens.expires_at` | **كامن** — يُحدَّث فقط عند `revoked = true`، والتوكن مُبطَل أصلاً | 📋 مُبلَّغ |
| `password_reset_grants.expires_at` | **كامن** — يُحدَّث فقط عند `used_at`، والمنحة مُستهلَكة أصلاً | 📋 مُبلَّغ |
| `appointment_reminders.remind_at` | **كامن** — `cancelRemindersForAppointment()` فقط، والتذكير مُلغى أصلاً | 📋 مُبلَّغ |
| `fiskaly_logs.created_at` | **كامن** (TSE مُطفأ) — لكنه **يخالف GoBD** عند التفعيل: طوابع سجل التدقيق يجب ألا تتغيّر | 📋 مُبلَّغ |

**لم أُصلح الأربعة** لأنها تمسّ الجدولة وسجل التدقيق وإعادة تعيين كلمة المرور — أنظمة لم أُحللها في هذه المهمة. الميجريشن الجاهز في القسم 8؛ قل الكلمة وأُطبّقه.

## 4. تقييم الحل الذي اقترحتُه في التدقيق

الحل المقترح كان:

```php
return DB::transaction(function () use (...) {
    $record = Otp::query()->where(...)->lockForUpdate()->first();
    if (!$record) return false;
    if ($record->attempts >= $maxAttempts) return false;
    $record->increment('attempts');
    ...
});
```

**الحل صحيح أمنياً في جوهره ويغلق السباق، لكنه ليس بديلاً مباشراً ولا يحقق كل ما نُسب إليه:**

| # | الملاحظة | الأثر |
|---|---|---|
| 1 | اسم دالة وتوقيع خاطئان (`verify` بدل `validate`، `OtpType` مفقود) | لا يعمل كبديل مباشر |
| 2 | عبارة «حتى لو انهار الطلب، المحاولة محسوبة» غير صحيحة داخل المعاملة؛ أي exception/rollback يعيد العدّاد كما كان | لا يحقق fail-closed عند فشل المعاملة |
| 3 | يجب أن تبقى شروط `used = false` و`expires_at > now()` داخل الاستعلام المقفول؛ عبارة «نفس شروط البحث» تفترض ذلك ولا تثبته | شرط صحة أساسي |
| 4 | المعاملة تمسك قفل الصف خلال القراءة والمقارنة والكتابة، وتحتاج معالجة أخطاء قاعدة البيانات/إعادة المحاولة وفق سياسة التطبيق | زمن قفل وتعقيد أكبر |
| 5 | UPDATE شرطية تحقق الضمان المطلوب بعبارة قصيرة وتثبت حجز المحاولة قبل المقارنة | أنسب لهذا العدّاد |

### لماذا اختيرت UPDATE شرطية بدل القفل

`generate()` يعمل داخل معاملة ويُنفّذ:

```php
$this->invalidateUnusedOtps($user, $type, $purpose);
// = UPDATE otps SET used = 1 WHERE email = ? AND purpose = ? AND used = 0
```

لو أمسك `validate()` قفلاً صفّياً عبر `lockForUpdate`، فإن طلب **«إعادة إرسال» أثناء تحقق جارٍ** قد ينتظر القفل نفسه الذي يحتاجه `invalidateUnusedOtps()`. هذا تنازع طبيعي يمكن ضبطه، وليس دليلاً حتمياً على deadlock؛ لكنه يطيل المقطع الحرج بلا حاجة في حالة عدّاد واحد.

القفل أيضاً:
- يحتاج معاملة لكل تحقق
- يُبقي القفل ممسوكاً عبر عدة رحلات ذهاب وإياب
- يحتاج سياسة واضحة لمعالجة فشل المعاملة، وقد يحتاج إعادة محاولة لأخطاء قاعدة البيانات القابلة للإعادة

**كل هذا لحماية عدّاد واحد.** الأداة الأنسب أبسط بكثير.

## 5. الحل المطبَّق: عبارة UPDATE شرطية ذرّية

المبدأ: **انقل الحارس إلى داخل `WHERE`**، فتُقيّمه قاعدة البيانات وتُنفّذ الزيادة كعملية واحدة غير قابلة للتجزئة.

```php
protected function claimAttempt(int $otpId, int $maxAttempts): bool
{
    return Otp::query()
        ->whereKey($otpId)
        ->where('attempts', '<', $maxAttempts)   // ← الحارس داخل الاستعلام
        ->where('used', false)
        ->where('expires_at', '>', now())
        ->update(['attempts' => DB::raw('attempts + 1')]) === 1;
}
```

**عدد الصفوف المتأثرة هو الجواب:**
- `1` → هذا المستدعي يملك محاولة، ويجوز له تقييم تخمينه
- `0` → الحدّ مستنفَد (أو السجل استُهلك أو انتهى بين القراءة والآن)

بما أن الشرط والكتابة في عبارة واحدة، **تُسلسِل قاعدة البيانات المتنافسين داخلياً**. توجد `max_attempts` فتحة لكل رمز، وكل طلب إما يطالب بواحدة بالضبط أو يُردّ.

### لماذا هذا أفضل من القفل

| | `lockForUpdate` + معاملة | UPDATE شرطية |
|---|---|---|
| معاملة مطلوبة | ✅ نعم | ❌ لا |
| قفل ممسوك عبر رحلات متعددة | ✅ نعم | ❌ لا |
| التنازع مع `generate()` | أعلى لأن القفل يبقى حتى نهاية المعاملة | أقل لأن القفل داخلي لعبارة واحدة |
| أثر rollback بعد حجز المحاولة | يلغي الزيادة | الحجز مكتمل قبل المقارنة |
| عبارات حجز المحاولة | قراءة مقفولة + تحديث داخل المعاملة | UPDATE شرطية واحدة |
| نفس الضمان | ✅ | ✅ |

### السلوك الكامل بعد الإصلاح

```php
public function validate(...): bool
{
    $record = $this->latestLiveOtp($target, $type, $purpose);
    if (!$record) return false;

    $maxAttempts = max(1, (int) config('otp.max_attempts', 5));

    // (١) طالِب بفتحة — أو ارحل
    if (!$this->claimAttempt($record->id, $maxAttempts)) {
        $this->burn($record->id);        // الحدّ مستنفَد -> اقتل الرمز
        return false;
    }

    // (٢) الآن فقط يجوز تقييم التخمين
    if (!hash_equals((string) $record->otp, $otp)) {
        if ((int) Otp::query()->whereKey($record->id)->value('attempts') >= $maxAttempts) {
            $this->burn($record->id);
        }
        return false;
    }

    // (٣) رمز صحيح -> استهلكه بكتابة محروسة
    return $this->burn($record->id);
}

protected function burn(int $otpId): bool
{
    return Otp::query()
        ->whereKey($otpId)
        ->where('used', false)           // ← الحارس يجعل الاستهلاك مرة واحدة
        ->update(['used' => true]) === 1;
}
```

### ثلاث نقاط دقيقة

**١. قراءة السرّ بلا قفل آمنة.** قيمة `otp` لا تتغيّر لصفّ معيّن، فمقارنتها بالقيمة المقروءة سابقاً صحيحة. المتغيّر الوحيد هو `attempts`، وهو محروس داخل `claimAttempt`.

**٢. `hash_equals` لا `===`.** موجودة في الكود الأصلي وأبقيتُها — المقارنة العادية تسرّب الرمز حرفاً بحرف عبر فروق زمن الاستجابة.

**٣. `burn()` محروسة بـ `used = false` — وهذا أغلق سباقاً ثانياً لم أكن قد لاحظتُه.** في الكود القديم، طلبان متزامنان بالرمز **الصحيح** كانا **كلاهما ينجحان**. والاستهلاك مرة واحدة خاصية جوهرية: نجاح التحقق يُستبدَل بسلطة حقيقية (منحة إعادة تعيين كلمة مرور، حساب موثَّق).

> **مقايضة واعية:** لو ضغط المستخدم «تحقق» مرتين سريعاً بالرمز الصحيح، الطلب الأول ينجح والثاني يُرجع `false`. هذا هو السلوك الصحيح لسرّ يُستخدم مرة واحدة، لكنه قد يُظهر خطأً للعميل إن استخدم الاستجابة الثانية. مع تحديد المعدّل من `AUTH-01`، الحماية من النقر المزدوج مسؤولية العميل.

### 6.2 الميجريشن الجديد

```sql
ALTER TABLE `otps` MODIFY `expires_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
```

**لماذا SQL خام لا `->change()`؟** لأن `$table->timestamp('expires_at')->change()` يُعيد إصدار `TIMESTAMP NOT NULL` مجرّداً — فيُعيد إطلاق قاعدة MySQL نفسها ويُرجع `ON UPDATE`. **تسمية DEFAULT صراحةً هي ما يُلغي الإسناد التلقائي**، فلا بد من كتابة التعريف كاملاً.

الميجريشن أيضاً يتقاعد الرموز التي أفسدها العطل:

```php
DB::table('otps')->where('used', false)->where('expires_at', '<=', now())
    ->update(['used' => true]);
```

**تحقق بعد التطبيق:**
```
COLUMN_NAME: expires_at   EXTRA: ""      ← فارغ، ON UPDATE اختفى
```

- اختبار الـschema يتخطّى — علة `ON UPDATE CURRENT_TIMESTAMP` خاصة بـ MySQL ولا وجود لها في sqlite.
- اختبار «خطأ ثم صحيح» **ينجح على sqlite بغض النظر عن الإصلاح** — فهو لا يحرس العلة في CI.

الحارس الفعلي ضد عودة العلة هو **الميجريشن نفسه** (الschema صار صحيحاً)، واختبار الـschema الذي يعمل إن وُجّهت المجموعة إلى MySQL. وقد تحققتُ يدوياً مقابل MySQL الحقيقي — النتائج في 7.1 و7.2 كلها من قاعدة بياناتك الفعلية.

> ⚠️ **لا تُشغّل** `DB_CONNECTION=mysql php artisan test` على قاعدة التطوير — `RefreshDatabase` سيمسحها. استخدم قاعدة اختبار منفصلة إن أردت تشغيل اختبار الـschema.

## 8. الأعمدة الأربعة المتبقية — ميجريشن جاهز

كلها **كامنة** (لا ضرر نشط اليوم)، لكنها نفس العلة وستنفجر عند أول تغيير في تلك المسارات. لم أُطبّقها لأنها خارج نطاق AUTH-02:

```php
public function up(): void
{
    if (DB::getDriverName() !== 'mysql') {
        return;
    }

    // توكن تحديث عمره 30 يوماً يجب ألا يُعاد ضبطه بأي كتابة
    DB::statement('ALTER TABLE `refresh_tokens` MODIFY `expires_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP');

    // منحة إعادة تعيين كلمة المرور — نفس المنطق
    DB::statement('ALTER TABLE `password_reset_grants` MODIFY `expires_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP');

    // موعد إطلاق التذكير يجب ألا يتحرك عند تعديل الصف
    DB::statement('ALTER TABLE `appointment_reminders` MODIFY `remind_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP');

    // طابع سجل تدقيق TSE — يجب أن يكون ثابتاً (GoBD)
    DB::statement('ALTER TABLE `fiskaly_logs` MODIFY `created_at` TIMESTAMP NULL DEFAULT NULL');
}
```

**أهمها `fiskaly_logs.created_at`:** عند تفعيل TSE، سجل تدقيق تتغيّر طوابعه الزمنية عند أي كتابة **يخالف مبدأ عدم القابلية للتغيير في GoBD** مباشرة.

**قل الكلمة وأُطبّقه.**

## 9. الأثر على ثغرات أخرى

| الثغرة | الأثر |
|---|---|
| **`AUTH-01`** (حدود المعدّل) | **تكامل، لا تكرار.** حدود المعدّل تُقلّل عدد الطلبات الواصلة؛ حدّ المحاولات يحرس السرّ نفسه. لو رفع أحدهم `RL_OTP_VERIFY_PER_DESTINATION` عالياً، يبقى الحدّ الآن صامداً — وهذا بالضبط سبب وجوب إصلاح الاثنين. **الثابت يجب أن يُفرَض حيث عُرِّف، لا في طبقة الشبكة.** |
| **`AUTH-03`** (الـ OTP نصّي صريح) | **غير متأثرة.** الحدّ يمنع التخمين عبر الشبكة، لا قراءة قاعدة البيانات. تجزئة الـ OTP ما زالت مطلوبة. |
| **علة `expires_at`** | **جديدة — لم تكن في التقرير الأصلي.** أُصلحت هنا لأنها شرط مسبق. أوصي بإضافتها إلى التقرير كبند مستقل. |

## 10. قبل النشر

```bash
# 1) طبّق الميجريشن على الإنتاج
php artisan migrate --force

# 2) تحقق من اختفاء ON UPDATE
php artisan tinker --execute="dd(DB::selectOne(\"SELECT EXTRA FROM information_schema.COLUMNS WHERE TABLE_SCHEMA=DATABASE() AND TABLE_NAME='otps' AND COLUMN_NAME='expires_at'\"));"
# متوقع: EXTRA = ""

# 3) شغّل اختبارات الحماية
php artisan test --filter=OtpAttemptCapTest
```

**لا حاجة لأي تغيير في `.env`.** الميجريشن يتخطّى نفسه تلقائياً على غير MySQL، والكود يعمل على أي محرّك — `claimAttempt()` عبارة SQL قياسية.
