## 1. الفكرة في 30 ثانية

ثلاث طلبات متتالية:

```
1) POST /auth/forgot-password       →  الباك إند يرسل كود 6 خانات
                                        على الإيميل أو الـ SMS

2) POST /auth/password/verify-otp   →  ترسل الكود، تستلم reset_token
                                        (سلسلة 64 حرف، صالحة 15 دقيقة)

3) POST /auth/reset-password        →  ترسل reset_token + كلمة المرور الجديدة
                                        → تم
```

**أنت تختار القناة، لا الباك إند.** ترسل `registration_method: "phone"` فيصلك الكود بالـ SMS، أو `"email"` فيصلك بالبريد. الباك إند يبحث عن الحساب بالعمود المطابق للقناة التي اخترتها.

**نقطتان تفرّقان هذا الفلو عن أي فلو آخر في التطبيق:**

1. الخطوتان 1 و 2 **لا تصدران أي توكن دخول**. `reset_token` ليس توكن مصادقة — لا ترسله في هيدر `Authorization`، ولا تخزّنه في مخزن الجلسة الدائم.
2. بعد نجاح الخطوة 3، **كل توكنات المستخدم القديمة تُبطَل على السيرفر**. إذا كان المستخدم مسجّل دخول على هذا الجهاز أو غيره فقد خرج الآن. راجع [القسم 12](#12-حالات-حافة-يجب-التعامل-معها).

## 2. آلة الحالات — الشاشات والانتقالات

```
        ┌─────────────────────────────────────┐
        │  شاشة A: أدخل الإيميل أو الهاتف     │
        │  + مبدّل القناة (email / phone)     │
        └──────────────┬──────────────────────┘
                       │ POST /auth/forgot-password
        ┌──────────────┴───────────────────────────────────┐
        │                                                  │
   200 OK                            404 / 403 / 429 / 422
        │                                                  │
        ▼                                     اعرض الخطأ وابقَ في A
        │                                     (تفاصيل في القسم 6)
        │  خزّن مؤقتاً في ذاكرة الشاشة:
        │    registration_method, identifier,
        │    masked_destination, expires_in, resend_after
        ▼
┌───────────────────────────────────────┐
│  شاشة B: أدخل الكود                   │
│  اعرض masked_destination              │
│  عدّاد تنازلي = expires_in            │
│  زر "إعادة إرسال" معطّل = resend_after│
└──────────────┬────────────────────────┘
               │ POST /auth/password/verify-otp
   ┌───────────┴───────────┐
 200 OK                 422 INVALID_OTP
   │                       │
   │                  اعرض "كود خاطئ"
   │                  وابقَ في B ⚠️ راجع 12.2
   ▼
   خزّن reset_token في الذاكرة فقط
   ▼
┌────────────────────────────────────────┐
│  شاشة C: كلمة المرور الجديدة + تأكيدها │
│  اعرض شروط القوة مباشرة (القسم 8)      │
└──────────────┬─────────────────────────┘
               │ POST /auth/reset-password
   ┌───────────┴──────────────────┐
 200 OK                    422 (password) → ابقَ في C، أعد المحاولة
   │                       422 INVALID_RESET_TOKEN → ارجع إلى A
   ▼
امسح كل التوكنات المخزّنة محلياً
   ▼
┌────────────────────────────┐
│ شاشة تسجيل الدخول + توست   │
│ "تم تغيير كلمة المرور"     │
└────────────────────────────┘
```

## 3. الخطوة 1 — طلب الكود

```
POST /api/auth/forgot-password
Content-Type: application/json
Accept: application/json
```

### الـ Payload

**استعادة عبر SMS:**

```json
{
  "registration_method": "phone",
  "phone": "+491701111111"
}
```

**استعادة عبر الإيميل:**

```json
{
  "registration_method": "email",
  "email": "customer@example.com"
}
```

| الحقل | النوع | إلزامي | ملاحظات |
|---|---|---|---|
| `registration_method` | `"email"` \| `"phone"` | ✅ دائماً | غير حسّاس لحالة الأحرف (يُحوّل لصغيرة) |
| `email` | string | ✅ إذا كانت الطريقة `email` | يجب أن يكون إيميل صالحاً |
| `phone` | string | ✅ إذا كانت الطريقة `phone` | حد أقصى 20 حرفاً |
| `locale` | `"ar"` \| `"de"` \| `"en"` | ❌ | يحدد لغة الرسائل — راجع [القسم 9](#9-اللغة-والترجمة) |

### الرد الناجح — `200 OK`

<div dir="ltr">


```json
{
  "success": true,
  "message": "تم إرسال رمز إعادة تعيين كلمة المرور إلى رقم هاتفك.",
  "registration_method": "phone",
  "verification_channel": "phone",
  "masked_destination": "*********1111",
  "expires_in": 600,
  "resend_after": 60
}
```


| الحقل | كيف تستخدمه |
|---|---|
| `masked_destination` | **اعرضه في شاشة B** — "أرسلنا الكود إلى `*********1111`". لا تعرض الرقم الكامل. |
| `expires_in` | **بالثواني.** عدّاد تنازلي لصلاحية الكود (600 = 10 دقائق). عند وصوله للصفر عطّل حقل الإدخال واعرض زر "إعادة إرسال". |
| `resend_after` | **بالثواني.** المدة التي يجب أن يبقى فيها زر "إعادة إرسال" معطّلاً (60). |
| `registration_method` / `verification_channel` | نفس القيمة، مكرّرة للتوافق. استخدم أياً منهما لتقرير أيقونة الشاشة (📱 أو ✉️). |

</div>


**شكل القناع:**

| الأصل | القناع |
|---|---|
| `+491701111111` | `*********1111` (آخر 4 أرقام ظاهرة) |
| `mail-customer@example.com` | `ma***********@example.com` (أول حرفين + النطاق) |

## 4. الخطوة 2 — التحقق من الكود

```
POST /api/auth/password/verify-otp
```

### الـ Payload

**أرسل نفس حقول الخطوة 1 + الكود.** لا تعتمد على أي جلسة سيرفر — احتفظ بـ `registration_method` والوجهة في حالة الشاشة ومرّرها ثانيةً.

```json
{
  "registration_method": "phone",
  "phone": "+491701111111",
  "otp": "482913"
}
```

| الحقل | النوع | إلزامي |
|---|---|---|
| `registration_method` | `"email"` \| `"phone"` | ✅ |
| `email` \| `phone` | string | ✅ حسب الطريقة |
| `otp` | string | ✅ (حد أقصى 10 أحرف) |

> أرسل `otp` **كنص** لا كرقم — الأصفار البادئة (`012345`) جزء من الكود.

### الرد الناجح — `200 OK`

```json
{
  "success": true,
  "message": "تم التحقق من الرمز. يمكنك الآن اختيار كلمة مرور جديدة.",
  "reset_token": "8kQm2vXpL9...RtY3nB7wZ",
  "expires_at": "2026-07-26T14:05:12+00:00"
}
```

| الحقل | كيف تستخدمه |
|---|---|
| `reset_token` | 64 حرفاً. **خزّنه في متغيّر داخل حالة شاشة C فقط.** لا في `localStorage`، لا في `SharedPreferences`، لا في هيدر `Authorization`. |
| `expires_at` | **ISO 8601** (ليس ثوانٍ!). صالح 15 دقيقة. إذا انتهت وشاشة C ما زالت مفتوحة، أعد المستخدم إلى شاشة A. |

### ⚠️ الكود يُستهلك هنا

بمجرد نجاح هذه الخطوة، **الكود المُدخل صار محروقاً على السيرفر**. لا يمكن استخدامه مرة ثانية. إذا رجع المستخدم للخلف من شاشة C إلى شاشة B وأدخل نفس الكود سيحصل على `422 INVALID_OTP`.

**التعامل الصحيح:** بعد نجاح الخطوة 2، انتقل لشاشة C بحيث **لا يستطيع زر الرجوع إعادته لشاشة B** (استبدل الشاشة في المكدّس بدل الدفع فوقها). إذا كان لا بد من السماح بالرجوع، أعده إلى شاشة A لا B.

## 5. الخطوة 3 — تعيين كلمة المرور

```
POST /api/auth/reset-password
```

### الـ Payload (الشكل المعتمد)

```json
{
  "reset_token": "8kQm2vXpL9...RtY3nB7wZ",
  "password": "NewPass@2026",
  "password_confirmation": "NewPass@2026"
}
```

| الحقل | إلزامي | ملاحظات |
|---|---|---|
| `reset_token` | ✅ | من الخطوة 2 |
| `password` | ✅ | راجع [القسم 8](#8-قواعد-كلمة-المرور) |
| `password_confirmation` | ✅ | يجب أن يطابق `password` تماماً، وإلا `422` على حقل `password` |

> **لا ترسل `registration_method` / `email` / `phone` / `otp` مع `reset_token`.** وجود `reset_token` هو ما يجعل الباك إند يسلك المسار الحديث.

### الرد الناجح — `200 OK`

```json
{
  "success": true,
  "message": "تم تغيير كلمة المرور بنجاح."
}
```

### 🚨 ما يجب أن تفعله فوراً بعد `200`

1. **امسح كل بيانات المصادقة المخزّنة محلياً** — `access_token`، `refresh_token`، كائن المستخدم المخبّأ. صارت كلها ميتة على السيرفر.
2. **امسح `reset_token` من الذاكرة.**
3. **انقل المستخدم لشاشة تسجيل الدخول** مع رسالة نجاح.
4. **لا تحاول تسجيل الدخول تلقائياً** — الـ API لا يرجّع أي توكن هنا بشكل مقصود.

> إذا كنت تخزّن رقم الهاتف/الإيميل، املأ به حقل تسجيل الدخول مسبقاً لتسهيل الأمر على المستخدم.

### الشكل القديم (Legacy — لا تستخدمه في كود جديد)

نفس النقطة تقبل أيضاً الشكل القديم بطلب واحد، وهو مدعوم فقط حتى تنقرض النسخ المنشورة من التطبيق:

```json
{
  "registration_method": "email",
  "email": "customer@example.com",
  "otp": "482913",
  "password": "NewPass@2026",
  "password_confirmation": "NewPass@2026"
}
```

عيبه: لا تستطيع التحقق من صحة الكود قبل أن يكتب المستخدم كلمة المرور، فيضطر لإعادة كتابتها إذا كان الكود خاطئاً.

## 6. جدول الأخطاء الشامل

**كل استجابات الخطأ التي يولّدها هذا المتحكّم لها نفس الشكل:**

```json
{
  "success": false,
  "error_code": "USER_NOT_FOUND",
  "message": "لا يوجد حساب مطابق لهذه البيانات."
}
```

> **اعتمد على `error_code` في المنطق، واعرض `message` للمستخدم.** الرسالة مترجمة وقد تتغير؛ الكود ثابت.

| HTTP | `error_code` | النقطة | المعنى | ما تفعله |
|---|---|---|---|---|
| `404` | `USER_NOT_FOUND` | 1، 2، 3(قديم) | لا حساب بهذه الوجهة | اعرض خطأ تحت حقل الإدخال: "هذا الرقم/الإيميل غير مسجّل". أضف زر "إنشاء حساب". |
| `403` | `ACCOUNT_DISABLED` | 1، 2، 3 | الحساب معطّل إدارياً | اعرض `message` كما هي مع زر "تواصل مع الدعم". **لا تعرض إعادة المحاولة** — لن تنفع. |
| `429` | `OTP_COOLDOWN` | 1 | طلبت كوداً قبل انقضاء الـ 60 ثانية | الرد يحوي `retry_after` (ثوانٍ). عطّل الزر وشغّل العدّاد بهذه القيمة. |
| `422` | `INVALID_OTP` | 2، 3(قديم) | كود خاطئ **أو** منتهٍ **أو** محروق | راجع [12.2](#122-فشل-الكود-له-ثلاثة-أسباب-غير-متمايزة) — الرسالة الموحّدة مقصودة. |
| `422` | `INVALID_RESET_TOKEN` | 3 | التوكن مستخدم أو منتهٍ أو غير موجود | أعد المستخدم إلى شاشة A ليبدأ من جديد. |

### أخطاء التحقق (Validation) — `422` بشكل لارافيل القياسي

**هذه لا تحوي `error_code`.** ميّزها بوجود مفتاح `errors`:

<div dir="ltr">


```json
{
  "message": "The given data was invalid.",
  "errors": {
    "password": [
      "The password field must contain at least one symbol.",
      "The password field must contain at least one uppercase and one lowercase letter."
    ],
    "phone": ["The phone field is required."]
  }
}
```

</div>


اربط كل مفتاح في `errors` بحقل النموذج المقابل واعرض العنصر الأول من مصفوفته (أو كلها).

### `429` من الـ Rate Limiter (مختلف عن `OTP_COOLDOWN`)

حدود لكل عنوان IP، فوق الـ cooldown:

| النقطة | الحد |
|---|---|
| `/auth/forgot-password` | 5 طلبات / دقيقة |
| `/auth/password/verify-otp` | 10 طلبات / دقيقة |
| `/auth/reset-password` | 10 طلبات / دقيقة |

شكل الرد هنا **مختلف** — من لارافيل مباشرة، بلا `error_code`:

```json
{ "message": "Too Many Attempts." }
```

مع هيدر `Retry-After` بالثواني.

**قاعدة التمييز:**

```
if (status === 429) {
    if (body.error_code === "OTP_COOLDOWN")  → استخدم body.retry_after
    else                                      → استخدم هيدر Retry-After
}
```

## 7. الأرقام التي يجب أن تعرفها

| القيمة | المدة | من أين تعرفها |
|---|---|---|
| طول الكود | 6 خانات | ثابت (اضبط طول حقل الإدخال) |
| صلاحية الكود | 10 دقائق | `expires_in` = `600` |
| cooldown إعادة الإرسال | 60 ثانية | `resend_after` = `60` |
| **محاولات خاطئة قبل حرق الكود** | **5** | غير مذكور في الرد — راجع [12.2](#122-فشل-الكود-له-ثلاثة-أسباب-غير-متمايزة) |
| صلاحية `reset_token` | 15 دقيقة | `expires_at` (ISO 8601) |

> اقرأ `expires_in` و `resend_after` **من الرد** ولا تكتبهما ثابتين في التطبيق — قابلة للضبط من جهة السيرفر ونيّتنا أن تتغير دون إصدار تطبيق جديد.

## 8. قواعد كلمة المرور

**مطابقة تماماً لقواعد التسجيل** — نفس القيود، فلا تفاجئ المستخدم:

| القاعدة | مثال يفشل |
|---|---|
| 8 أحرف على الأقل | `Ab@1` |
| حرف كبير وحرف صغير | `newpass@123` |
| رقم واحد على الأقل | `NewPass@` |
| رمز واحد على الأقل | `NewPass123` |
| `password_confirmation` مطابق | — |

✅ صالحة: `NewPass@2026` · `Look#Up99` · `Barber!Shop7`

**نفّذ هذا التحقق في الواجهة قبل الإرسال** واعرض قائمة شروط حيّة تتحوّل لعلامات ✓ أثناء الكتابة. تذكّر أن فشل التحقق هنا يعني رحلة شبكة ضائعة — بينما الـ `reset_token` يبقى صالحاً، فالمستخدم لا يخسر تقدّمه.

## 9. اللغة والترجمة

كل حقول `message` تأتي مترجمة من السيرفر بثلاث لغات: **ar / de / en**.

**طريقتان لتحديد اللغة (الأولوية بهذا الترتيب):**

1. حقل `locale` في الـ body: `"locale": "ar"`
2. هيدر `Accept-Language`: `Accept-Language: ar` أو `ar-SY,ar;q=0.9,en;q=0.8`

أي لغة أخرى تُتجاهل ويُستخدم الافتراضي.

**التوصية:** أرسل هيدر `Accept-Language` على كل طلبات الـ API (interceptor عام) مضبوطاً على لغة التطبيق الحالية. هذا يغطي هذا الفلو وغيره.

> إذا كنت تفضّل رسائل من ملفات ترجمة التطبيق نفسه، استخدم `error_code` كمفتاح وتجاهل `message`. الحقلان موجودان لهذا السبب.

## 10. حقل `otp` في الرد — متى يظهر ولماذا

في بعض البيئات يحوي رد الخطوة 1 حقلاً إضافياً:

```json
{ "success": true, "...": "...", "otp": "482913" }
```

يظهر في حالتين فقط:

1. `APP_DEBUG=true` (بيئة تطوير محلية)، أو
2. القناة SMS وبوابة Vonage غير مفعّلة — أي أن الكود **لن يصل فعلياً**، فيُعاد في الرد كي يبقى الفلو قابلاً للاختبار.

**قواعد التعامل:**

- ✅ استخدمه في بناء التطوير فقط لملء حقل الكود تلقائياً وتسريع الاختبار.
- ❌ **لا تبنِ عليه أي منطق إنتاجي.** في الإنتاج مع SMS مفعّل لن يكون موجوداً.
- ❌ **لا تعرضه في الواجهة في بناء الإنتاج** حتى لو وصل.

## 11. ماذا يحدث في الخلفية بالضبط

مفيد لفهم سبب كل سلوك — وللتشخيص عند العطل.

### عند الخطوة 1

1. يتحقق من الحقول → `422` عند الفشل.
2. يبحث عن المستخدم في العمود المطابق للقناة → `404` إن لم يوجد.
3. يفحص `is_active` → `403` إن كان معطّلاً.
4. يفحص هل مضت 60 ثانية على آخر كود لهذه الوجهة → `429` إن لا.
5. **يبطل كل الأكواد السابقة غير المستخدمة** لهذه الوجهة ولغرض إعادة التعيين، ثم يولّد كوداً جديداً.
   → **الأثر عليك:** إذا ضغط المستخدم "إعادة إرسال"، الكود القديم مات فوراً. إن كان قد أدخله قبل وصول الجديد سيفشل. اعرض تنبيهاً: "استخدم آخر كود وصلك".
6. يضع مهمة إرسال في الطابور (Mail أو Vonage SMS). **الرد يعود فوراً دون انتظار التسليم** — لذلك `200` تعني "قُبل الطلب"، لا "وصلت الرسالة".

### عند الخطوة 2

1. يجلب **الكود الحي الوحيد** لهذه الوجهة والغرض.
2. إن كان عدّاد المحاولات قد بلغ 5 → يحرق الكود ويرفض.
3. يقارن مقارنة ثابتة الزمن. عند الخطأ: `attempts++`، وإن بلغت 5 يُحرق الكود.
4. عند النجاح: يعلّم الكود مستخدماً، **يبطل أي `reset_token` سابق لنفس المستخدم**، ويصدر واحداً جديداً.
   → **الأثر عليك:** لا يمكن أن تكون عمليتا استعادة قيد التنفيذ لنفس الحساب. آخر عملية تفوز.

### عند الخطوة 3

داخل معاملة واحدة:

1. يحدّث كلمة المرور.
2. **يوثّق القناة المستخدمة** — استعادة عبر SMS تضبط `phone_verified_at`، وعبر الإيميل تضبط `email_verified_at`.
   → **الأثر عليك:** المستخدم غير المفعّل الذي أتم الاستعادة **لن يُرمى إلى شاشة تفعيل OTP** عند تسجيل الدخول التالي. اعتبر حسابه مفعّلاً.
3. **يحذف كل `access_token` ويبطل كل `refresh_token`** للمستخدم على كل الأجهزة.
4. يستهلك الـ grant ويبطل أي grants أخرى.

**لماذا هذا التدمير؟** إعادة تعيين كلمة المرور هي العلاج لحساب مخترق. لو بقيت التوكنات القديمة صالحة لظلّ المهاجم داخل الحساب رغم تغيير الضحية لكلمة المرور.

### "الـ API نجح لكن ما وصلني كود"

بالترتيب — أبلغ الباك إند بما تشاهده:

1. هل هناك **queue worker** يعمل؟ بدونه يُسجّل الكود في قاعدة البيانات ولا يُرسل أبداً، والـ API يرجّع `200`.
2. هل بوابة Vonage مضبوطة ومفعّلة؟ إن لا، تُتخطّى الرسالة **بصمت** ويُكتب سطر في اللوغ (وسيظهر الكود في الرد — راجع القسم 10).
3. هل صيغة رقم الهاتف مطابقة تماماً لما هو مخزّن؟ راجع [12.1](#121-صيغة-رقم-الهاتف--أهم-مطب).

## 12. حالات حافة يجب التعامل معها

### 12.1 صيغة رقم الهاتف — أهم مطب

**الباك إند يقارن أرقام الهواتف كنصوص خام. لا يوجد أي تطبيع.**

| مخزّن في الحساب | المستخدم أدخل | النتيجة |
|---|---|---|
| `+491701111111` | `+491701111111` | ✅ يعمل |
| `+491701111111` | `00491701111111` | ❌ `404` |
| `+491701111111` | `0170 1111111` | ❌ `404` |
| `+491701111111` | `+49 170 1111111` | ❌ `404` |

**مسؤوليتك:** طبّع الرقم في الواجهة إلى **نفس الصيغة المستخدمة عند التسجيل** قبل الإرسال، في كل من `register` و `login` و `forgot-password`. الصيغة المتّبعة في النظام: **E.164** — علامة `+`، ثم رمز الدولة، ثم الرقم، بلا مسافات أو شرطات أو أقواس.

استخدم مكتبة رقم هاتف حقيقية (`libphonenumber` / `intl_phone_field`) مع منتقي دولة، ولا تعتمد على إدخال المستخدم الحر.

> عند وصول `404` على رقم يقسم المستخدم أنه مسجّل — الصيغة هي المشتبه به الأول.

### 12.2 فشل الكود له ثلاثة أسباب غير متمايزة

`422 INVALID_OTP` يعني واحداً من ثلاثة **دون تمييز في الرد**:

1. الكود خاطئ.
2. الكود انتهت صلاحيته (> 10 دقائق).
3. الكود محروق (5 محاولات خاطئة، أو مُستخدم سابقاً، أو أُبطل بطلب كود جديد).

**هذا إخفاء متعمّد** — التمييز يعطي المهاجم معلومة مجانية.

**كيف تعوّض عن ذلك في الواجهة:**

- شغّل عدّاد `expires_in` محلياً؛ عند وصوله للصفر **اعرض "انتهت صلاحية الكود" واعرض زر إعادة الإرسال** بدل انتظار خطأ السيرفر.
- **عُدّ المحاولات الفاشلة محلياً.** بعد 3 محاولات اعرض تلميحاً: "تأكد من آخر رسالة وصلتك، أو اطلب كوداً جديداً". بعد 5 اقترح إعادة الإرسال بوضوح، لأن الكود صار محروقاً بالتأكيد وأي محاولة أخرى ستفشل حتماً.
- اجعل زر "إعادة إرسال" ظاهراً دائماً (معطّلاً مع عدّاد) لا مخفياً.

### 12.3 المستخدم أغلق التطبيق بين الخطوات

- **بين 1 و 2:** الكود صالح 10 دقائق. إن كنت تحفظ حالة الشاشة (`registration_method` + الوجهة فقط — لا شيء سري)، استأنف مباشرة على شاشة B وسيقبل السيرفر الكود الذي وصله. وإلا ابدأ من A، لكن انتبه: استدعاء الخطوة 1 من جديد **يبطل الكود الذي وصله** ويرسل غيره — وقد يصطدم بالـ cooldown (`429`) إن لم تمضِ 60 ثانية.
- **بين 2 و 3:** `reset_token` في الذاكرة فقط، فقد ضاع. ابدأ من A. **لا تخزّنه على القرص لإنقاذ هذه الحالة** — الخطر الأمني أكبر من الإزعاج.

### 12.4 المستخدم مسجّل دخول ويستخدم "نسيت كلمة المرور"

سيناريو واقعي (يتذكر أنه نسيها قبل انتهاء الجلسة). بعد نجاح الخطوة 3 تُبطَل جلسته الحالية.

**تعامل:** بعد `200` امسح حالة المصادقة وانقله لتسجيل الدخول — حتى لو كان "داخل" التطبيق. أي طلب مصادق بعد ذلك سيرجع `401`.

> إذا كان المستخدم مسجّل دخول ويعرف كلمة مروره الحالية، وجّهه إلى `POST /api/profile/change-password` بدلاً من هذا الفلو.

### 12.5 حسابات Google

حساب أُنشئ عبر Google قد لا يملك كلمة مرور إطلاقاً. هذا الفلو **يعمل معه** ويضع له كلمة مرور لأول مرة، فيصير قابلاً للدخول بالطريقتين. لا يحتاج معالجة خاصة منك — بشرط أن يملك الحساب إيميلاً أو هاتفاً تبحث به.

### 12.6 عدم استقرار الشبكة

الخطوة 1 **ليست idempotent**: كل استدعاء ناجح يولّد كوداً جديداً ويبطل السابق. لا تعد المحاولة تلقائياً عند انتهاء المهلة (timeout) — قد يكون الطلب الأول نجح، فتُبطل كوداً وصل للمستخدم فعلاً.

**تعامل:** عند timeout في الخطوة 1، انقل المستخدم لشاشة B على أي حال مع رسالة "إذا لم يصلك الكود خلال دقيقة، اضغط إعادة إرسال". دع القرار له.

```ts
const API = `${BASE_URL}/api`;

type ResetChannel = 'email' | 'phone';

interface ApiError {
  success: false;
  error_code?: string;                 // غائب في أخطاء التحقق
  message: string;
  retry_after?: number;                // مع OTP_COOLDOWN فقط
  errors?: Record<string, string[]>;   // أخطاء التحقق فقط
}

async function post<T>(path: string, body: unknown, locale = 'ar'): Promise<T> {
  const res = await fetch(`${API}${path}`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Accept': 'application/json',
      'Accept-Language': locale,
    },
    body: JSON.stringify(body),
  });

  const data = await res.json();

  if (!res.ok) {
    throw Object.assign(new Error(data.message ?? 'Request failed'), {
      status: res.status,
      body: data as ApiError,
      retryAfterHeader: Number(res.headers.get('Retry-After')) || undefined,
    });
  }

  return data as T;
}

/** الوجهة كما يفهمها الـ API — طبّع الهاتف إلى E.164 قبل الوصول إلى هنا. */
function destination(channel: ResetChannel, identifier: string) {
  return channel === 'phone'
    ? { registration_method: 'phone', phone: identifier }
    : { registration_method: 'email', email: identifier };
}

// ───────────────────────────── الخطوة 1
interface ForgotResponse {
  success: true;
  message: string;
  registration_method: ResetChannel;
  masked_destination: string;
  expires_in: number;    // ثوانٍ
  resend_after: number;  // ثوانٍ
  otp?: string;          // بيئات التطوير فقط
}

const requestCode = (channel: ResetChannel, identifier: string) =>
  post<ForgotResponse>('/auth/forgot-password', destination(channel, identifier));

// ───────────────────────────── الخطوة 2
interface VerifyResponse {
  success: true;
  message: string;
  reset_token: string;
  expires_at: string;    // ISO 8601
}

const verifyCode = (channel: ResetChannel, identifier: string, otp: string) =>
  post<VerifyResponse>('/auth/password/verify-otp', {
    ...destination(channel, identifier),
    otp: otp.trim(),
  });

// ───────────────────────────── الخطوة 3
const setNewPassword = (resetToken: string, password: string) =>
  post<{ success: true; message: string }>('/auth/reset-password', {
    reset_token: resetToken,
    password,
    password_confirmation: password,
  });
```

### التعامل مع الأخطاء في الواجهة

```ts
function handleResetError(err: any, ctx: 'request' | 'verify' | 'commit') {
  const { status, body, retryAfterHeader } = err;

  // أخطاء التحقق: اربطها بحقول النموذج
  if (status === 422 && body?.errors) {
    return { type: 'fieldErrors' as const, fields: body.errors };
  }

  switch (body?.error_code) {
    case 'USER_NOT_FOUND':
      return { type: 'inline' as const, message: body.message, action: 'signup' };

    case 'ACCOUNT_DISABLED':
      return { type: 'blocking' as const, message: body.message, action: 'support' };

    case 'OTP_COOLDOWN':
      return { type: 'cooldown' as const, seconds: body.retry_after ?? 60 };

    case 'INVALID_OTP':
      // قد يكون خاطئاً أو منتهياً أو محروقاً — الرسالة موحّدة عمداً
      return { type: 'inline' as const, message: body.message, action: 'resend' };

    case 'INVALID_RESET_TOKEN':
      return { type: 'restart' as const, message: body.message };
  }

  // 429 من الـ rate limiter (بلا error_code)
  if (status === 429) {
    return { type: 'cooldown' as const, seconds: retryAfterHeader ?? 60 };
  }

  return { type: 'inline' as const, message: 'حدث خطأ، حاول مرة أخرى.' };
}
```

## 14. قائمة فحص قبل التسليم

- [ ] رقم الهاتف مطبّع إلى **E.164** في `register` و `login` و `forgot-password` بنفس الطريقة
- [ ] `otp` يُرسل **كنص** (الأصفار البادئة محفوظة)
- [ ] `expires_in` و `resend_after` مقروءان **من الرد** لا مكتوبَين ثابتين
- [ ] عدّاد الصلاحية يعرض "انتهت صلاحية الكود" محلياً قبل أن يفشل السيرفر
- [ ] زر "إعادة إرسال" ظاهر دائماً، معطّل مع عدّاد `resend_after`
- [ ] المحاولات الفاشلة معدودة محلياً مع تلميح بعد 3 واقتراح إعادة إرسال بعد 5
- [ ] `reset_token` في الذاكرة فقط — لا `localStorage` / `SharedPreferences` / هيدر `Authorization`
- [ ] الانتقال لشاشة C **يستبدل** شاشة B في مكدّس التنقل
- [ ] `password_confirmation` مُرسل ومطابق
- [ ] قواعد قوة كلمة المرور مطبّقة محلياً مع شروط حيّة (8+، كبير، صغير، رقم، رمز)
- [ ] بعد نجاح الخطوة 3: **مسح كل التوكنات المحلية** والانتقال لتسجيل الدخول
- [ ] لا تسجيل دخول تلقائي بعد الاستعادة
- [ ] `429` مع `OTP_COOLDOWN` مميّز عن `429` من الـ rate limiter (`Retry-After`)
- [ ] أخطاء التحقق (`errors`) مربوطة بحقول النموذج
- [ ] `Accept-Language` مُرسل على كل الطلبات
- [ ] حقل `otp` في الرد غير مستخدم ولا معروض في بناء الإنتاج
- [ ] لا إعادة محاولة تلقائية للخطوة 1 عند انتهاء المهلة
